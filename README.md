# SecurityLab 0.1.0 — контрольная точка M1/M2

**Рабочее ядро и проверенный учебный цикл. Это ещё не готовая AI-система.**

Две будущие AI-роли: Red Team и Blue Team. Dashboard запланирован как основной интерфейс; минимальный CLI и отчёты сохраняются. CS AIReviewer не подключается.
В этой версии роли выполняет детерминированный сценарий `scripted-demo-no-ai`.
Он не ищет неизвестные уязвимости: воспроизводит заранее заданную ошибку доступа
на синтетических данных и проверяет заранее подготовленное исправление.

## Быстрый запуск без Docker

Нужны Python 3.11+ и Git в PATH. Сторонних Python-библиотек для ядра и тестов нет.
Распакуйте архив, откройте PowerShell **в папке, содержащей этот README**:

```powershell
py -3 -m securitylab doctor
py -3 -m unittest discover -s tests -v
py -3 -m securitylab demo
py -3 -m securitylab status
```

Для Linux замените `py -3` на `python3`. Команды проверены здесь на Linux/Python 3.12;
Windows-проверка пока NOT TESTED. Установка пакета через pip для этого не нужна.
Запускайте команды из каталога проекта, а не из внешней папки архива.

`demo` выводит ID прогона. Он создаёт только `.securitylab` внутри текущей папки:

- `state.sqlite3` — состояния, находки, доказательства и история;
- `runs/<ID>/repo` — новый учебный Git-репозиторий;
- `runs/<ID>/events.jsonl` — журнал;
- `runs/<ID>/report/report.html` и `report.json` — отчёт.

Откройте HTML двойным щелчком. Готовый пример лежит в `examples/report.html`.
`FIXED` в нём означает исправление **одной учебной ошибки**, а не проверку вашего продукта.

## Команды

```powershell
py -3 -m securitylab --state .securitylab init
py -3 -m securitylab --config config.example.toml demo
py -3 -m securitylab demo --enqueue
py -3 -m securitylab worker
py -3 -m securitylab worker --run <ID>
py -3 -m securitylab status <ID>
py -3 -m securitylab findings <ID>
py -3 -m securitylab history <ID>
py -3 -m securitylab stop <ID>
py -3 -m securitylab retry <ID>
py -3 -m securitylab report <ID> --output reports
py -3 -m securitylab rollback <ID>
```

Общие параметры `--state`, `--config` указываются **до** подкоманды.
`<ID>` заменяется фактическим ID без угловых скобок.
`worker` последовательно обрабатывает существующую очередь и завершается; это не фоновый сервис.
`retry` только возвращает остановленную/заблокированную задачу в очередь, затем нужен `worker`.
Лимит по умолчанию — три запуска на задачу, включая восстановление после аварии.
`stop` кооперативный: тестовый процесс прерывается при очередной проверке флага;
Git-команда завершается в пределах своего тайм-аута.

`rollback` создаёт обратный коммит только в ветке учебного исправления. Основная ветка
не меняется, находка становится `REOPENED_AFTER_ROLLBACK`. Старые доказательства сохраняются
как история. После отката сформируйте новый отчёт; прежний HTML — снимок на прежний момент.
Чтобы пройти новый цикл после отката, создайте новый `demo`.

`scan <путь>` намеренно возвращает BLOCKED/код 2: произвольный проект ещё нельзя
безопасно запустить. Команда не читает и не изменяет его файлы.
Код 0 — успешная операция CLI, 2 — блокировка/ошибка/неподтверждённое исправление;
успешное добавление в очередь не означает успешную проверку.

## Что проверяет учебный цикл

1. Создаёт исходную ветку `main` с известной ошибкой проверки владельца записи.
2. Запускает защищённый набор из семи проверок: четыре проходят, три проверки доступа падают.
3. Регистрирует подтверждённую находку только при точном ожидаемом результате.
4. Создаёт ветку `securitylab/<ID>`, добавляет проверку владельца и два регрессионных теста.
5. Запускает регрессию, компиляцию, обязательный набор и отдельный повторный прогон исходного набора.
6. Валидатор сверяет коды завершения, тайм-ауты, хеши тестов/исходника, ревизии и чистоту Git.

Пустой результат, сбой процесса, изменённый тест, старый коммит или заявление «исправлено»
не могут заменить доказательства. Нулевого exit code недостаточно.

## Восстановление и обновление

- После аварийного завершения: `worker --run <ID>`. Пройденные стадии сохраняются в SQLite.
- После Ctrl+C/`stop`/блокировки: устранить причину, `retry <ID>`, затем `worker --run <ID>`.
- Журнал JSONL восстанавливается из транзакционной истории SQLite через `report`.
- Перед переносом или обновлением остановите worker и скопируйте **весь** каталог состояния,
  включая возможные `state.sqlite3-wal`/`state.sqlite3-shm`, при закрытых процессах.
- Не удаляйте состояния автоматически. Для чистого стенда укажите новую папку `--state`.
- Схема SQLite v1; неизвестные версии отвергаются. Миграции более новых схем ещё не реализованы.
- Для продолжения разработки сначала прочитайте `docs/STATE.md`.

В ZIP включён `SecurityLab.git.bundle` — Git-история этой контрольной точки.
Восстановление в новый каталог: `git clone SecurityLab.git.bundle SecurityLab-dev`.
Исходники в корне архива можно использовать сразу без восстановления Git.

## Следующий шаг: проверка контейнера (S1)

После обновления исходников выполните из папки проекта:

```powershell
docker compose build
docker compose run --rm --entrypoint python demo -m securitylab.sandbox_check
```

При ошибке сборки остановитесь. Проверка выводит JSON со статусом каждого из 16 условий.
Общий PASS означает прохождение перечисленных проверок, а не сертификацию песочницы.
Результат сохраняется в Docker-томе: `/data/isolation_checks/<ID>.json`.
Отсутствующие cgroup v2/данные дают BLOCKED; слабые ограничения — FAIL.
Не подключайте произвольные проекты или AI-инструменты только на основании этого PASS.
Проверка не создаёт нагрузку до исчерпания памяти/PID и не проверяет все способы выхода из контейнера.

## S2: одноразовое исполнение задач

Проверка S1 на ПК пользователя завершена: все 16 условий PASS.
Следующая актуальная проверка — новый broker/runner:

```powershell
docker compose build
py -3 -m securitylab.container_runner --self-test
```

Он запустит пять сценариев в отдельных контейнерах без тома состояния, папок ПК и сети.
Подробности и ограничения: `docs/S2_RUNNER.md`. Прежний demo ещё не переведён на S2.

## Этап 3 / S3: полный учебный цикл через Docker

S2 подтверждён на ПК: все пять сценариев и cleanup PASS.
Следующий актуальный запуск после обновления:

```powershell
docker compose build
py -3 -m securitylab demo --executor docker
```

Ожидаются DONE и `finding_status: FIXED`. Это всё ещё известный учебный пример без AI,
но все пять проверок запускаются через одноразовые контейнеры, а их записи сверяются
на хосте. Подробнее: `docs/S3_WORKFLOW.md`. Старый `demo` без параметра остаётся локальным.
