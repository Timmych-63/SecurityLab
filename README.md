# SecurityLab — учебная платформа Red/Blue-исследования контроля доступа на локальной LLM

Проект в статусе **v0.1.0 (M1/M2), текущий этап S11.4 (2026-11-20)**.

SecurityLab — это не сканер уязвимостей и не продукт для аудита чужих систем.
Это учебная платформа, на которой локальная LLM (qwen3.5:2b через Ollama, без
облака) проходит полный исследовательский цикл:

1. **Красные (Red)** — модель изучает документацию и код учебного приложения
   инструментами `read` / `search` / `http`, формулирует гипотезы о нарушениях
   контроля доступа вида «актор X на путь Y должен получить статус Z, основание —
   пункт документации» и проверяет их разрешёнными запросами.
2. **Независимое подтверждение** — каждая гипотеза, расходящаяся с наблюдением,
   воспроизводится на свежем стенде отдельно от исходного исследования.
   Итоговые состояния гипотез: `consistent` / `unconfirmed` / `confirmed` / `refuted`.
3. **Синие (Blue)** — только подтверждённые нарушения. Патч строится в изолированной
   Git-копии, проходит baseline → candidate → recheck и попадает в отдельный коммит.
   Автоисправление ограничено рамками: ожидаемые отказы 401/403, наличие
   контрольного ответа 200 (якорь body-hash), лимит проблем на цикл.

> **Важно:** отсутствие находок не означает безопасность приложения.
> Всё исследуемое — учебные приложения с подготовленной документацией
> ожидаемого поведения, а не боевые системы.

## Что уже работает

- Живой цикл Красных на локальной модели: гипотеза → разрешённая проверка →
  наблюдение → вердикт; сбой одного решения не теряет остальные результаты.
- Навигация покрытия: ядро считает непроверенные пары «путь × актор» и
  подсказывает их модели блоком `SUGGESTED NEXT PROBES` (без подсказок дефектов).
- Независимое подтверждение на свежем стенде по каждой гипотезе.
- Blue-конвейер в изолированной Git-копии (код готов, живой сценарий подготовлен).
- Дашборд (React) как основной интерфейс: подготовка проекта, запуск прогона,
  ход решений, гипотезы и наблюдения.
- 421 автоматический тест (модель и наблюдатель имитируются; живые прогоны — отдельно).

## Требования

- Windows 10/11 (проверялось на Windows), PowerShell 5.1;
- Docker Desktop (контейнеры Hermes/worker, Ollama, приватная сеть `securitylab-ai-private`);
- Python 3.11+ с лаунчером `py`;
- Git (для ведения истории и изолированных исправлений);
- Модель qwen3.5:2b подтягивается контейнером `model-pull` (профиль `setup`)
  в локальный том Ollama. Никаких внешних API-ключей — модель только локальная.

## Быстрый старт

```powershell
# конфигурация AI (один раз): скопировать пример и поправить при необходимости
Copy-Item .\ai.example.toml .\ai.local.toml

# запуск стека и дашборда (после перезагрузки ПК или заново)
powershell -ExecutionPolicy Bypass -File .\scripts\Start-SecurityLab.ps1
```

Скрипт ждёт готовность контейнера модели, печатает адрес дашборда. Прогоны
исследования запускаются из интерфейса дашборда. Обновления ставятся
архивами-обновлениями и скриптом вида `apply_S11_4.ps1` (см. `README_S11_4_RU.md`).

Проверка работоспособности модели и тестов:

```powershell
py -3 -m securitylab ai-smoke
py -3 -m unittest discover -s tests -v
```

## Как подключить исследуемое приложение

Нужны два файла (пример — учебное приложение AuthzNotes):

- Markdown-документация **ожидаемого поведения**: пользователи, права, маршруты,
  идентификация. Без списков дефектов и готовых сценариев — документация описывает
  приложение, а не подсказывает, где искать дыры (`examples/research/authznotes.md`);
- конфигурация аккаунтов и бюджета (`examples/research/authznotes.setup.json`):
  акторы и роли, лимиты времени/решений/запросов.

Оба файла загружаются в дашборде на этапе подготовки проекта; входные копии
фиксируются с SHA-256. Поддерживаемый профиль первого поколения: локальное
FastAPI-приложение, идентификация через доверенный заголовок `X-Test-User`.

## Артефакты прогона

- `.securitylab/research/<ид>/summary.json` — итоговая сводка: статус, причина
  остановки, покрытие (`coverage`), заметки;
- `.securitylab/research/<ид>/decision_NN.json`, папки стадий `http_NN/` —
  пошаговые решения и независимые наблюдения;
- `.securitylab/ai/<ид>/calls/` — «квитанции» всех обращений к модели
  (промпты, ответы, отклонения валидатора).

## Структура репозитория

| Каталог | Назначение |
|---|---|
| `securitylab/` | ядро: цикл исследования (`research_cycle.py`), контракт решений (`research_contract.py`), DTO дашборда |
| `dashboard/` | React-интерфейс (`src/`) и собранная сборка (`dist/`, используется как есть) |
| `scripts/` | операционные скрипты (`Start-SecurityLab.ps1`) |
| `examples/research/` | учебный сценарий AuthzNotes (документация + конфигурация) |
| `docs/` | детальные описания этапов, план, статус |
| `tests/` | автоматические тесты (421) |

## Границы и безопасность

- Модель выполняется локально в Docker-контейнере без выхода во внешние сети;
  рабочие контейнеры без привилегий, с ограничением процессов и памяти.
- Бюджеты (время, решения, запросы) enforced программно, а не обещанием модели.
- Автозапуск кода исследуемого проекта — только в разрешённом контейнерном
  профиле; произвольный `scan` чужих репозиториев запрещён.
- Blue-исправления ограничены статусами 401/403 с контрольным якорем 200 и
  попадают только в изолированную Git-копию — исходный код не меняется напрямую.

## История этапов

Проект развивается этапами S1 → S11.4; каждый этап имеет отдельный отчёт:

- текущий: `README_S11_4_RU.md` (фикс краша ядра на финальных гипотезах без `action`);
- предыдущие: `README_S11_3_RU.md`, `docs/S11_1_RESEARCH_CYCLE_RU.md`,
  `docs/RESEARCH_PLAN_RU.md` (план и критерии приёмки), `docs/STATE.md` (статус).

Следующая контрольная точка — живой полный цикл с исправлением (Blue) на
подготовленном сценарии AuthzNotes и расширение покрытия на TicketDesk.
