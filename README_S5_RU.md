# S5 — проверка фактического предложения Blue

Обновление поверх S4.4. Распакуйте архив в папку с compose.yaml,
compose.ai.yaml и каталогом securitylab с заменой файлов.
Состояние и модель не удаляются. Docker Desktop должен быть запущен.

## Первая проверка: сохранённое предложение, без вызова модели

Выполняйте по одной команде. При ошибке остановитесь и пришлите вывод.

```powershell
py -3 -m unittest discover -s tests -v
docker compose build
py -3 -m securitylab candidate-check --summary ".\.securitylab\ai\f79a9dcef7214c88850078ced6ddf94c\summary.json"
```

Ожидается mode=actual-candidate-docker-fixture, status=PASS,
finding_status=FIXED. Это новый запуск проверки, а не изменение старого
отчёта S4.4. В proofs три независимых контейнерных запуска: baseline,
candidate и recheck. В каждом 15 сценариев.

В .securitylab/candidate_checks/<id>/ сохраняются candidate.txt — точный
предложенный код, receipts — квитанции исполнения, summary.json — результат.
Для этого режима пока нет HTML-отчёта, записи в старой очереди S3 и resume.

## Новый полный AI-запуск после успешной первой проверки

```powershell
docker compose -f compose.ai.yaml --profile build build hermes
docker compose -f compose.ai.yaml up -d model
docker compose -f compose.ai.yaml exec -T model ollama list
py -3 -m securitylab ai-demo --verify-candidate
```

Дождитесь готовности модели. Повторный pull не нужен. Флаг --verify-candidate
включает S5. Без него ai-demo сохраняет прежний режим S4.4 с канонизацией.

## Что действительно изменилось

Исполняется исходное содержимое Blue.content, без замены на готовое исправление.
Совпадение AST с одним из четырёх образцов больше не требуется в S5.
Ожидания задаются кодом проверяющего на хосте; контейнер возвращает наблюдения,
а не утверждение об успехе. Проверяются 401/404, доступ владельцев и запрет
чужого доступа. Исходный уязвимый код должен показывать ожидаемый дефект.
Сбой, тайм-аут, подмена квитанции, неверный результат или неудачная очистка
не приводят к FIXED.

## Ограничения

Это всё ещё учебный проект, а не загрузчик произвольных приложений.
RECORDS и сигнатура функции фиксированы. Разрешены присваивания локальным
record/owner, if/return, сравнения, ограниченные выражения и RECORDS.get(record_id).
Импорт, файловые операции, вывод, циклы, рекурсия, произвольные вызовы и изменение
контейнеров данных запрещены. Этот допуск ограничивает возможности кода, но
сам по себе не подтверждает правильность: заведомо неверная логика может
дойти до тестов и будет отклонена по поведению.

Тестовый модуль находится в том же контейнере/процессе, что и приложение.
Его целостность здесь обеспечивается ограничением языка и неизменяемой
рецептурой задания, а не отдельной ОС-изоляцией от приложения. Это нельзя
переносить на произвольный Python без нового механизма проверки.
PASS подтверждает только фиксированные сценарии; проверки не скрыты от автора
кода и могут быть специально обойдены логикой под тесты. Обобщённая проверка
реальных проектов потребует отдельных границ доверия и расширения сценариев.

Локальные тесты используют имитацию Docker-транспорта и выполняют только
константы, написанные разработчиком. Реальный Docker/Qwen S5 ещё нужно
проверить на вашем компьютере.
