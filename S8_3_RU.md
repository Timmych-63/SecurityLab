# SecurityLab S8.3 — понятные результаты и проверка сценариев dashboard

Обновление поверх S8.2.1. Дизайн и ограничения S7.2 сохранены.

## Изменения

- Время округляется до миллисекунд до разделения на минуты/секунды: `4 мин 52.13 с`, без хвостов floating point. Некорректные и отрицательные значения показываются как «—». Переходы 60 секунд и 60 минут обработаны.
- Завершение этапа не считается доказательством исправления. Предложения Red/Blue и прочие завершённые шаги — нейтральные.
- `ACCESS_POLICY_VIOLATION_REPRODUCED` у baseline: «Нарушение воспроизведено». У кандидата/повторной проверки: «Нарушение сохранилось — исправление не прошло проверку», оранжевый маркер.
- `ACCESS_POLICY_MATCHED`: «Проверенные случаи соответствуют политике», зелёный маркер. Это не универсальная гарантия безопасности и не замена итогов ядра.
- Та же семантика цветов применена к графику длительности этапов и легенде.
- Причина завершения сохраняется в job и финальном событии, в том числе при штатном возврате BLOCKED исполнителем. Ранее в job попадали преимущественно исключения dashboard, а результат содержал только BLOCKED.
- Для старых запусков причина из summary показывается внутри журнала, если её ещё нет в событиях. Если причина отсутствует, UI честно сообщает об этом. Причина рендерится как текст, не HTML.
- Бесшовное обновление S8.2.1 сохранено.

## Установка

1. Дождитесь завершения текущего прогона или отмените его и дождитесь результата.
2. Остановите dashboard через Ctrl+C.
3. Скопируйте **содержимое** папки `update` в корень проекта с заменой файлов. В корне должны быть папки securitylab и dashboard.
4. Запустите:

```powershell
py -3 -m securitylab.dashboard --state "$env:TEMP\SecurityLab_S72_DemoState"
```

5. Откройте http://127.0.0.1:8765 и один раз нажмите Ctrl+F5.

Docker-образы пересобирать не нужно. Готовый dashboard/dist включён; npm нужен только для разработки. Новое сохранение причин событий применяется к новым прогонам, UI fallback работает и со старыми summary.

## Что проверено автоматически

- 11 существующих тестов dashboard: профили моделей, привязка конфигурации, snapshot, ограничения API, восстановление после перезапуска, HTTP/CSRF и раздача UI.
- 11 тестов S8.2: отмена, cleanup, отдельные diff кандидатов, события, восстановление.
- 2 новых теста S8.3: причина BLOCKED в job/events/detail после перезапуска; список запусков, сохранённый PASS, экспорт патча и чтение evidence; запрет экспорта при BLOCKED.
- React/jsdom: заполнение формы нового прогона, обязательная предпроверка, сброс допуска при смене модели, передача выбранной конфигурации и переход в созданный прогон.
- React/jsdom: сохранение вкладки/фильтров/фокуса, ошибки связи, устаревшие ответы, прекращение опроса завершённого прогона; текст ошибки с HTML не создаёт HTML-элементы.
- Формат времени на граничных значениях, семантика статусов, существующие DTO-тесты.
- TypeScript + Vite production build.

Тесты API используют подставной исполнитель, а UI — подставной адаптер. Это проверяет маршрутизацию данных и поведение, но не заменяет полный прогон реальной модели/Docker в браузере. Проверка реальной геометрии/цветов в браузере этой среды недоступна. Полную пользовательскую приёмку этапа dashboard пока не считаем закрытой.

Команды разработки:

```powershell
py -3 -m unittest discover -s tests -p "test_dashboard.py" -v
py -3 -m unittest discover -s tests -p "test_s82.py" -v
py -3 -m unittest discover -s tests -p "test_s83.py" -v
cd dashboard
npm ci
npm run test:results
npm run test:launch
npm run test:refresh
node scripts/test-dto.mjs
npm run build
```

## Приёмка на вашем ПК

1. Откройте прошлый BLOCKED: время короткое, кандидат с сохранившимся нарушением подписан явно. Если summary содержит error, причина видна в журнале.
2. Выберите другую AI-конфигурацию в новом запуске: перед стартом должна требоваться актуальная предпроверка.
3. Запустите проверку, смените вкладку, прокрутите: обновления не должны сбрасывать просмотр.
4. При необходимости отмените и дождитесь результата. Посмотрите причину и артефакты; STOPPED не является исправлением.
5. При PASS откройте diff и экспортируйте патч. При BLOCKED экспорт подтверждённого патча должен быть недоступен. Не нужно добиваться PASS от слабой модели ради проверки интерфейса; этот пункт можно проверить на имеющемся успешном прогоне поддерживаемого режима.

Далее: приёмка нового небольшого FastAPI-проекта вне подготовленных примеров; затем многофайловый анализ/патчи. Универсальная проверка любых приложений не реализована этим обновлением.
