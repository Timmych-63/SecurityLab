# S5.1 — задание Blue и диагностика ответа

Обновление поверх S5. Распакуйте в текущую папку проекта с заменой файлов.
Модель и сохранённые запуски не удаляются. Код проверки кандидата и ограничения
исполнения не ослаблены; готовый FIXED за модель не подставляется.

Изменения:
- В текст задания модели больше не включается весь транспортный JSON с role,
  schema_version, verification и retry. Эти поля остаются в проверяемом запросе.
- Исходный модуль и структурированные аргументы доступа передаются отдельно.
  Непроверенное описание Red не передаётся Blue как основание исправления.
- Повторная попытка строится из исходного модуля и статических замечаний.
  Сырой ошибочный ответ остаётся в квитанциях, но не повторяется в контексте модели.
- Лишние JSON-поля больше не прекращают диагностику доступного content:
  отмечаются также отсутствие RECORDS, аннотации/изменение сигнатуры, импорты,
  неподдерживаемые вызовы и нарушение порядка исходных проверок.
- Неверный ответ по-прежнему отклоняется. Диагностика не выполняет код.

Выполняйте по одной команде; при ошибке остановитесь:

```powershell
py -3 -m unittest discover -s tests -v
docker compose -f compose.ai.yaml --profile build build hermes
docker compose -f compose.ai.yaml up -d model
docker compose -f compose.ai.yaml exec -T model ollama list
py -3 -m securitylab ai-demo --verify-candidate
```

Модель должна отвечать на ollama list перед ai-demo. Повторный pull и пересборка
securitylab-demo не нужны: проверочный runner в этом обновлении не изменён.

Ожидаемый успешный режим: hermes-actual-candidate-fixture, PASS/FIXED и ссылка
verification_record. Улучшение задания не гарантирует правильный ответ модели.
При BLOCKED пришлите итог и execution.stderr квитанции calls, указанной в error;
не запускайте повторно многократно без диагностики.
