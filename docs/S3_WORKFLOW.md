# Этап 3 / S3 — оркестратор + одноразовый runner

## Что изменилось

`demo --executor docker` проходит те же стадии очереди, но baseline, regression,
build, mandatory и recheck запускаются через S2 в пяти отдельных контейнерах.
Основная очередь, SQLite, Git и валидатор остаются на стороне доверенного оператора.
Docker-режим сохранён в runs.mode; после прерывания worker восстанавливает его автоматически.
Недоступность Docker даёт BLOCKED, а не запуск кода на хосте.
Схема базы остаётся v1, старые локальные прогоны продолжают читаться.

Для каждой проверки broker сохраняет JSON-запись на хосте. В ней:
- ID прогона и назначение проверки;
- Git revision, source_hash, test_hash, payload_sha256;
- immutable image ID, stdout/stderr, реальные коды завершения attach и daemon;
- признаки timeout/cancel/truncation/OOM и результат cleanup.

В SQLite хранится ссылка на запись и SHA-256 её байтов. Перед финальным вердиктом
DockerFixtureRunner повторно читает записи и сверяет связи, хеши, результаты и
уникальность пяти receipt ID. Отсутствие/изменение/перестановка записей не дают FIXED.
Исходный тест также должен доказать ошибку до патча и пройти после него.

## Граница доверия — принципиально

Принимается только точное совпадение исходника с VULNERABLE/FIXED из fixture.py,
а регрессионного теста — с константой REGRESSION. Подготовка payload происходит из
проверенных констант. Поэтому код теста/сервиса известен и не может быть произвольно
заменён моделью, а его проверенный результат связан с исполнением в контейнере.

Это НЕ универсальная защита от подделки результатов произвольной программой.
Произвольный код способен фальсифицировать stdout и выходить с кодом 0. Самостоятельный
`container_runner --job` по-прежнему помечает вывод недоверенным и не закрывает находки.
Переход к реальным проектам потребует независимых проверок поведения и нового контракта
доказательств. Локальный пользователь с доступом и к SQLite, и к JSON-записям доверенный:
хеширование не является цифровой подписью и не защищает от такого пользователя.

S3 доказывает соединение очереди/runner/доказательств на известном учебном примере.
Red/Blue пока сценарные, модель и Hermes ещё не подключены.

## Проверка на Windows

Из папки проекта после распаковки обновления:

```powershell
docker compose build
py -3 -m securitylab demo --executor docker
```

Вторую команду выполнять после успешной сборки. Она запускается на Windows-хосте,
не внутри demo-контейнера: только доверенный broker имеет доступ к Docker.
Ожидаем stage/status DONE, mode scripted-demo-docker-no-ai, finding_status FIXED.
Команда выведет абсолютный путь к HTML-отчёту. Прогон сохраняется в .securitylab/runs/<ID>:
repo/, receipts/, events.jsonl, report/. Контейнеры получают только JSON-пакет исходников.

Если Docker Desktop не запущен, результат BLOCKED; после запуска Docker:

```powershell
py -3 -m securitylab retry <ID>
py -3 -m securitylab worker --run <ID>
py -3 -m securitylab report <ID>
```

Для очереди без немедленного запуска: `demo --executor docker --enqueue`, затем `worker`.
`stop <ID>` из другого PowerShell передаёт отмену текущему контейнерному запуску, после
чего broker выполняет cleanup. При аварийном убийстве самого broker возможны остатки;
порядок ручного восстановления приведён в S2_RUNNER.md, автоматический reaper ещё впереди.

Локальный режим `demo` сохранён для совместимости и запуска без Docker. Для приёмки
этого этапа обязательно указывать `--executor docker`; повтор S1/S2 не требуется.

## Проверки

Негативные сценарии: пропавшая/изменённая запись, чужой run ID, перестановка проверок,
неправильный payload, неуспешный cleanup, неподтверждённый текст FIXED, изменённый
исходник, отмена и отсутствие Docker. Проверяется восстановление после CONFIRMED
без повторного baseline и последовательная обработка Docker/локальных задач.
В тестах интеграции Docker-транспорт подменён явно обозначенным FixtureBroker,
который выполняет только ранее проверенные константы локально. Это не живой Docker PASS.
Фактический полный S3-прогон нужно подтвердить на ПК пользователя.
