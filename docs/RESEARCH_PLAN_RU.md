# План SecurityLab: самостоятельное исследование

Цель: Red изучает приложение и выбирает гипотезы; исполнитель собирает наблюдения; независимая проверка подтверждает нарушение; Blue предлагает патч; повторные и регрессионные проверки определяют результат.
Документация описывает приложение, а не готовые сценарии. Текст проекта и Markdown — данные, не источник полномочий для агента. Бюджеты и инструменты ограничивает исполнитель.

## Обновление S11.0 — входные данные
Добавлены prepare-research, Markdown TicketDesk, отдельная конфигурация аккаунтов и бюджета. Создаются копии входных данных, их SHA-256 и статическая карта исходников. Не вызываются модель, Docker, установочные скрипты или исходный код проекта.
PREPARED означает только подготовку документов. execution_ready=false. Новые настройки пока не используются старым запуском из UI. Запуск автономного исследования ещё не реализован.

## Аудит основы
Повторно используем снимки, проверку хешей, контейнерный исполнитель, сбор наблюдений, Git-копии кандидатов, отмену и журнал UI. Старые режимы S9/S10 сохраняем для совместимости; не выдаём их за новый цикл.
Не переносим в новый вход обязательные готовые cases, списки дефектов и ожидаемые хеши HTTP-ответов. Для независимого подтверждения потребуется отдельное представление проверяемого ожидаемого поведения с указанием основания из документации; свободный MD сам по себе не даёт машинного вердикта.
Текущая статическая карта ограничена 8 модулями /18 КБ, прямыми FastAPI-декораторами, подготовленными зависимостями, без внешних БД. Это ограничение первой версии, не поддержка любого приложения.

## Следующее изменение
Подключить подготовку к UI и проверку реальной готовности стенда. Затем добавить единый цикл исследовательских решений с учётом бюджета, сохранением частичного результата и точными причинами остановки. Разрешения не берутся из Markdown.

## Приёмка
TicketDesk и минимум второй проект; отдельные случаи без дефектов, с воспроизводимым дефектом, неподдерживаемыми зависимостями, ошибкой формата AI, таймаутом и отменой. Логи живой модели обязательны для приёмки; подмены модели в тестах подтверждают только механику. Отсутствие находок не означает безопасность приложения.
Каждое обновление: пункт плана, выполненные проверки, непроверенное на живом стенде, следующий критерий.
