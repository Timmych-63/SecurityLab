# S11.1 — единый вход и самостоятельный цикл исследования

Это второе обновление этапа 1 и первые реализации этапов 2–4 плана `docs/RESEARCH_PLAN_RU.md`.
Старые режимы (S7.2/S9/S10, демо) сохранены без изменений; их тесты проходят в полном составе.

## Что сделано

### Этап 1. Единый вход и подготовка (завершён в объёме кода)
- `POST /api/research/prepare` — подготовка из интерфейса: документация (Markdown до 12 КБ, загрузка файла или вставка),
  тестовые аккаунты, бюджет. Ядро проверяет снимок и статическую карту **до** вызова модели; конкретная причина
  отклонения возвращается как текст ошибки (неподдерживаемая зависимость, динамический роутер, нет маршрутов и т.п.).
- Подготовка сохраняет копии входных данных с SHA-256 (`knowledge.md`, `setup.json`, `application_map.json`).
- **Инвалидация**: новая подготовка того же снимка/сервиса/entry помечает предыдущую `SUPERSEDED`; запуск по
  отменённой подготовке отклоняется. Готовность привязана к точному входу через grant 120 с (как раньше).
- Полная предпроверка `research` перед запуском, по шагам с причинами: **подготовка → совместимость проекта →
  Docker → образы → модель (имя+digest) → запуск приложения** в изолированном стенде (smoke-GET статического маршрута).
- Пользовательский путь: Проект → описание приложения → настройки стенда → проверка готовности → запуск.
  Технический профиль (`research-v1`) выбирается системой; пользовательские внутренние режимы не показывает.
- CLI: `repo research-check PREP_ID` (статическая готовность), `repo research PREP_ID --execute`.

### Этап 2. Самостоятельный цикл Red (новый `research_cycle.py` + `research_contract.py`)
- Последовательный цикл: Red сама решает следующий шаг; исполнитель проверяет параметры, бюджет и границы.
- Минимальные инструменты: `read` (фрагмент исходника ≤80 строк/4500 байт), `search` (литеральный поиск),
  `http` (1–8 GET-проверок за ход только в подготовленном стенде через фиксированный независимый верификатор),
  финальные `hypotheses`. Полных исходников в промпте нет; карта — имена файлов и маршруты.
- Бюджет применяется программно: решения модели (1–30), HTTP-запросы Red (1–100), время (60–3600 с);
  независимые проверки верификатора учитываются отдельно (`verification_requests`).
- Каждое решение сохраняется (`decision_NN.json`) вместе с сырыми наблюдениями; гипотеза обязана ссылаться на
  выполненное Red HTTP-наблюдение.
- Ошибки формата: ограниченный повтор с обратной связью (один корректирующий запрос на решение; на транспортном
  уровне Hermes — свой отклонённый ответ с feedback). Некорректное действие не выполняется. Усечённый
  (`finish_reason='length'`), деградировавший (повторяющийся текст) и пустой ответ модели тоже считаются
  отклонённой попыткой: worker печатает `AI_ATTEMPT_JSON=...REJECTED` с причиной и feedback, адаптер выполняет
  один корректирующий запрос; повторная неудача → BLOCKED с сохранёнными накопленными результатами.
- Отдельно обрабатываются: таймаут модели, неверный ответ (дважды → BLOCKED с сохранёнными результатами),
  отказ инструмента (BLOCKED, накопленное сохраняется), исчерпание бюджета (штатное завершение с найденным),
  отмена (STOPPED только при подтверждённой очистке), завершение без гипотез (DONE, `NOT_EVALUATED`).

### Этап 3. Независимое подтверждение
- У гипотезы: файл, маршрут, актор, ожидание (по документации), наблюдение Red, результат воспроизведения
  на **свежем** стенде. Состояния: `unconfirmed → confirmed / refuted`, `consistent` (поведение совпало с
  документацией), `insufficient`. Найденное нарушение не создаётся из описания Red: статус ставит ядро.
- Привязка: snapshot pin (manifest SHA-256), binding с хешами проверок и payload, receipts Docker, аудит
  неизменности на каждом шаге (как в S7.2).

### Этап 4. Blue и проверка исправлений
- Blue получает подтверждённые проблемы, относящиеся исходники (≤8 файлов / 18 КБ), наблюдения статусов и документацию;
  возвращает минимальный патч (только изменённые выбранные файлы).
- Проверяющий: baseline на исходных источниках (ожидание — воспроизведённое нарушение), независимая проверка
  кандидата (deny 401/403 + body-hash контроли разрешённых ответов), recheck на свежем стенде, изолированный Git
  commit и diff. Две попытки Blue с реальной обратной связью.
- Исходный репозиторий и снимок не изменяются; merge не выполняется. Неудачный патч → `NEEDS_REVIEW` с причиной.

## Установка

Остановите dashboard (Ctrl+C) и сделайте резервную копию папки SecurityLab (`.securitylab` не изменяется).
Скопируйте содержимое `update/` из архива в корень существующего SecurityLab S11.0 с заменой файлов.
Настройки AI, `compose.ai.gpu.yaml` и сохранённое состояние не меняются.

## Ограничения первой версии

- Охват не изменился: небольшой многофайловый Python/FastAPI (до 31 модуля / 180 КБ, статические маршруты,
  зависимости пиннутого образа, без внешних БД). Другие стеки — после приёмки MVP через отдельные адаптеры.
- Автоисправление Blue поддерживает нарушения с ожидаемым статусом 401/403 и наличием разрешённого ответа 200
  (якорь контроля). Подтверждённые нарушения с ожиданием 404 или без якоря сохраняются как находки без патча.
- Red делает только GET-наблюдения с подстановкой `X-Test-User`; POST/другие методы — не в первой версии.
- Длина фрагментов чтения и транспорта фиксирована; слишком большой контекст Blue честно даёт
  `blue_context_too_large`, а не обрезается молча.
- Если усечённые ответы повторяются даже после корректирующего запроса, поднимите `max_output_tokens`
  в `ai.local.toml` (допустимо до 4096) — каждая попытка ограничена этим лимитом.
- Против зацикливания модели в `ai.local.toml` можно задать `frequency_penalty` и `presence_penalty`
  (необязательные числа 0..2; эти поля Ollama реально применяет на OpenAI-совместимом `/v1`).
  Начните с `frequency_penalty = 0.4` и `presence_penalty = 0.2`; если ключи не заданы — ничего
  не отправляется, действует поведение сервера по умолчанию.

## Хотфикс живого прогона: развёртывание и операционные замечания

- Код worker'а запечён в Docker-образ `securitylab-hermes:s4` (`COPY securitylab` в
  `docker/Hermes.Dockerfile`; монтирований нет — адаптер их запрещает). Замена файлов на хосте
  НЕ обновляет worker: после каждого применения update-архива пересоберите образ:
  `docker compose -f compose.ai.yaml --profile build build hermes` (слои кешируются, минута-две).
  Второй живой прогон прошёл по старому образу и потому повторил прежнее поведение без
  корректирующего повтора.
- Порядок обновления: применить update → пересобрать образ → обновить `ai.local.toml` →
  `py -3 -m securitylab ai-smoke`. Обратный порядок даст на каждый вызов
  `Unknown AI configuration keys`: worker в старом образе не знает новых ключей конфига.
- `Another worker owns this state directory` — это живой процесс, а не «мусорный файл»:
  dashboard держит OS-замок `<state>/dashboard_jobs/worker.lock` всё время работы. Закройте
  прежнее окно dashboard/CLI (или остановите процесс python), затем запустите снова.
  Удаление файла замка не требуется и не помогает; в сообщении теперь указан путь
  заблокированного каталога.

## Первый живой прогон (наблюдение и исправление)

Первый запуск с живой моделью qwen3.5:2b (ноябрь 2026): решение 1 выполнено штатно (HTTP-наблюдение),
на решении 2 модель превысила лимит выходных токенов и ушла в повторяющийся текст; Hermes вернул ошибку
разговора, и прогон завершался BLOCKED без корректирующего повтора — это расходилось с заявленной
обработкой «неверный ответ (дважды → BLOCKED)».

Исправлено: `hermes_worker.transport_rejection()` классифицирует усечённый/деградировавший/пустой ответ
как отклонённую попытку (REJECTED с причиной и feedback), `HermesAdapter.ask()` выполняет один
корректирующий запрос с этой обратной связью; причина попадает в итоговое сообщение и в квитанцию вызова
(`calls/<id>.json`). Накопленные результаты решений и HTTP-наблюдений сохраняются в любом случае
(проверено тестом, воспроизводящим живой отказ). Тесты: +7 (392 всего).

Дополнено по второму живому прогону (тот же отказ — образ не пересобран): см. «Хотфикс живого
прогона: развёртывание и операционные замечания». Добавлены необязательные
`frequency_penalty`/`presence_penalty` в конфиг AI (против повторов текста), информативное
сообщение о занятом state-каталоге. Тесты: +3 (395 всего).

Дополнено по третьему живому прогону (решение 1 штатно, решение 2 — TIMEOUT после 1200 с):
при медленной генерации деградировавший ответ не успевает доехать до лимита токенов до
хост-дедлайна `timeout_seconds` (максимум 1200 с), и прогон останавливается TIMEOUT —
корректирующий повтор не успевает включиться (для таймаута фидбека нет по определению).
Рекомендация: держать `max_output_tokens` умеренным (2048) — деградация гарантированно упирается
в лимит токенов раньше дедлайна и превращается в REJECTED с одним корректирующим повтором.

Исправлен разрыв на стыке транспорта и research-контракта (четвёртый прогон): при отклонении
ответа по контракту worker передавал сырой ответ модели (до 16000 байт) в поле `retry`
research-запроса, ограниченное 4000 байтами, — прогон падал с `Invalid research corrective
feedback` уже на построении повтора. Теперь для research-задач (red/blue) worker составляет
компактный корректирующий фидбек (причина отказа + инструкция, заведомо ≤ 4000 байт);
discovery/review/S7.2 сохраняют прежнее поведение (лимит 16000 байт, сырой ответ используется
намеренно). Квитанция вызова по-прежнему хранит сырой ответ целиком. Тесты: +4 (399 всего).

Дополнено по пятому живому прогону (решение 1 штатно, решение 2 — два отклонения схемы
http-проверок, остановка с сохранением накопленного): механика REJECTED + корректирующего
повтора отработала правильно (квитанции обеих попыток записаны), но корректирующий фидбек
был универсальным («ответьте одним JSON по схеме») без канонического примера, и модель
дважды исказила форму проверок — вероятный источник искажения: ключи method/file из дампа
ROUTES, которые модель переносила в проверки. Теперь `research_contract.corrective_instruction()`
/ `blue_corrective_instruction()` кладут в повтор причину отказа и канонические формы всех
действий (для http — точный состав ключей: только path и actor, «no method, headers, file
or notes»), а промпт Red явно требует «each check object has exactly the keys path and
actor» рядом с примером. Формат фидбека ограничен 2000 байтами, чтобы повтор гарантированно
проходил валидацию retry (≤ 4000 байт). Тесты: +5 (404 всего).

Дополнено по шестому живому прогону (20.11.2026, сборка S11.2) — первый полный живой цикл
этапов 2–3: гипотеза `/health` (актор anonymous, ожидание 200 по документации, наблюдение
Red 200) независимо подтверждена, статус `consistent` («соответствует документации»),
нарушений не найдено. Транспорт был здоров, автопроверка путей (`http_assist_NN`) не
понадобилась. Обратная сторона: всего 1 решение и 1 проверка — минимальный цикл для
qwen3.5:2b; модель завершает исследование сразу же, как только получает хоть одно
наблюдение, потому что промпт не показывает, какие категории документации остались
непокрытыми. Отдельное наблюдение UI: в карточке проверки колонка «Свежий стенд» для
consistent-гипотезы показала «—» (свежий стенд для неё по определению не запускался —
воспроизведение выполняется только для расхождений). В S11.3 сделано: ядро считает за
модель непроверенные пары ROUTES×ACTORS и отдаёт их в промпт блоком `SUGGESTED NEXT
PROBES` (только карта и акторы, без признаков дефектов) плюс правило системного покрытия
категорий (anonymous → каждый аккаунт → неизвестные ресурсы); в строки гипотез добавлены
идентификаторы стадий (`observed_stage`, `confirm_stage`), и UI объясняет пустую ячейку
«Свежий стенд» («не требовался: наблюдение совпало с документацией») вместо «—».

## Что не проверено на живой модели и Docker

Все механические проверки выполнены с имитацией модели и наблюдателя (404 теста PASS, включая 31 новый,
7 транспортных, 3 конфигурационных и 9 корректирующего фидбека). Живые прогоны состоялись и выявили/закрыли
разрывы обработки усечённых ответов и корректирующего фидбека, но полный живой цикл (гипотезы →
независимое подтверждение → Blue-патч) на этой сборке ещё не пройден.
Тесты механики не доказывают: что слабая модель найдёт проблему, что JSON-контракт выдержит реальную
генерацию, что старт приложения и верификатор сработают на вашем стенде. Приёмка MVP (этап 5) требует
отдельных живых прогонов.
