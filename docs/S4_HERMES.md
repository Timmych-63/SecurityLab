# S4 — Hermes + локальная модель, ограниченный учебный AI-цикл

## Статус

Реализация и автоматические проверки готовы. Live Docker/Hermes/Ollama на Windows:
NOT TESTED до получения вывода пользователя. Не объявлять весь этап принятым заранее.
S3 уже принят на ПК пользователя: d6f559e8291348529e92dc44e55fb3f4, DONE/FIXED,
scripted-demo-docker-no-ai, attempts=1, error=null.

## Что запускается

- Ядро остаётся на установленном Python пользователя, без новых зависимостей.
- Hermes в отдельном контейнере Python 3.14, исходники закреплены на
  e075441241b8d626789b4aae0e376f86eabf824d (репозиторий NousResearch/hermes-agent).
  Зависимости устанавливаются штатным `pm.build_env` из lock, без сборки wheel Hermes.
- Ollama 0.40.15, модель qwen3.5:2b, digest
  0689d44085e06d165161a8a9a1731344278cfb5aade63a3c3dbdb48ab54b130a.
- Контекст 64000 в сервере и Hermes. Проверка настоящего API выявила, что
  Qwen2.5-Coder/4096 несовместима с минимальным окном этой версии Hermes;
  ограничение не отключали и метаданные модели не подделывали.
- CPU-профиль для первого запуска: модель до 6 GiB/2 CPU, Hermes до 1.5 GiB/1 CPU.
  Нужна достаточная память Docker VM (ориентир не менее 8 GiB). Скорость и фактическое
  потребление на ноутбуке ещё не измерены. GPU этим этапом не сертифицируется.

## Запуск Windows

Распаковать обновление поверх S3 в папку с compose.yaml. Старое состояние не удалять.
Docker Desktop должен быть запущен. Из PowerShell в папке проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-S4.ps1
```

ExecutionPolicy применяется только к этому процессу PowerShell; постоянные настройки
системы не меняются. Скрипт останавливается при первой ошибке:
1. Собирает образ Hermes из закреплённого commit.
2. Загружает модель (~2.7 GB) во временном установочном контейнере с интернетом.
3. Запускает модель в отдельной внутренней сети, без опубликованных портов.
4. `py -3 -m securitylab ai-smoke`: один реальный ответ через Hermes.
5. `py -3 -m securitylab ai-demo`: Red → Blue → проверка AST → S3.

Ожидаются два результата PASS. У ai-demo дополнительно finding_status FIXED,
verification_run и пути report/record. При ошибке прислать её вывод; не заменять
команду на старый demo, он не проверяет AI. Повтор загрузки использует существующие слои.
Для повторных запусков достаточно ai-smoke / ai-demo при работающем model.
Остановка модели: `docker compose -f compose.ai.yaml stop model`.

## Честная граница результата

Red видит только VULNERABLE и предлагает описание + конкретную пару caller/record.
Blue получает тот же исходник и предложение Red, возвращает полный service.py.
Роли последовательные, отдельные процессы и контексты, без истории друг друга, кроме
явно переданного предложения Red. enabled_toolsets=[], память/контекстные файлы
отключены. Включённый инструмент или попытка tool call блокируют ответ.

Ответ — строгое JSON-предложение, не Evidence. Произвольные пути, статус FIXED от
модели, дублированные поля и чужие запросы не принимаются. AST Blue обязан точно
совпасть с проверенным FIXED (форматирование/кавычки/комментарии могут отличаться).
Иное, в том числе корректное альтернативное исправление, требует отдельного ревью.
Произвольный сгенерированный код не выполняется.

После допуска используется каноническое встроенное исправление с тем же AST и
проверенный S3-цикл. Его дочерняя запись честно остаётся scripted-demo-docker-no-ai.
Верхний AI-прогон имеет mode hermes-constrained-fixture и сохраняет оригинальные
предложения и связь с verification_run. PASS означает успех этого ограниченного
упражнения, а не готовность к аудиту произвольного проекта.

Оба ответа модели, их digest/request hash, image ID, фактические exit/status и cleanup
сохраняются в .securitylab/ai/<ID>/calls. Итог — summary.json. HTML-отчёт относится к
дочерней S3-проверке; AI-предложения находятся в summary.json, не маскируются как
результаты тестов. Локальный оператор и каталог состояния считаются доверенными.

## Изоляция и сбои

Hermes не получает mounts проекта/состояния/Docker socket. UID10001, read-only root,
cap-drop ALL, no-new-privileges, tmpfs /tmp, лимиты PID/RAM/CPU. Broker проверяет inspect
до start, ограничивает вывод/время (300 секунд на роль), сверяет exit daemon и удаляет
контейнер. Нет автоматического перехода на облачный API или host execution.

Сеть securitylab-ai-private internal: в штатной конфигурации только model и временный
Hermes. Установочный model-pull имеет интернет и завершается до AI; в рабочую сеть
его не подключаем. Содержимое образов/Compose и локальный Docker daemon доверенные.
Проверки конфигурации не являются доказательством защиты от всех container escapes.

Ctrl+C останавливает текущий AI-вызов и вызывает cleanup; при жёстком убийстве host
broker возможен оставшийся контейнер securitylab-ai-<ID>. Запись intent содержит имя.
Не удалять все контейнеры подряд. Автоматический reaper ещё не реализован.
AI-вызовы пока не возобновляются из SQLite: новый ai-demo создаёт новый AI-прогон.
Дочерняя S3-задача сохраняет прежние worker/retry/stop механизмы; её возобновление
само не переписывает старый AI summary. Для AI используется отдельная OS-блокировка.

## Проверки

109 тестов PASS: договоры JSON/AST, роли, отсутствие инструментов, чужие binding,
неуспешный cleanup, timeout/OOM, недоступность provider, отказ до исполнения,
полный цикл с явно подменёнными AI/Docker транспортами. Журнал test-s4-output.txt.

Дополнительно: реальное окружение Python 3.14 + закреплённый Hermes установлено через
pm.build_env; импорт AIAgent, инициализация с tools=[] и run_conversation прошли с
локальным подставным HTTP model endpoint. Это API compatibility PASS, не real AI PASS.
Воспроизводимый probe: scripts/probe_hermes_api.py --hermes-source <checkout>, запуск
интерпретатором окружения Hermes. Вывод: hermes-api-probe-output.txt.
Docker отсутствует в среде разработки: сборка образа и live модель NOT TESTED.
