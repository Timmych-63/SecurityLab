# SecurityLab S6.3a — guarded standalone Python Docker probe

## Purpose / explicit boundary

After S6.2.2 Windows snapshot tests (18/18 PASS, user-provided), the first
**limited real-code** execution path is introduced. The operator explicitly
selects one UTF-8 `.py` file from a content-verified repository snapshot and
passes `--execute`. The broker passes that exact source as `task.py` through its
existing stdin contract into an ephemeral, single-process Python container.
The module is NOT run on the host. There are no installed third-party project
dependencies and no service startup, multi-file imports, API client or business
behavior assertions.

This is NOT a real repository security scanner or complete Python/FastAPI
profile. There is no Red/Blue patch cycle, no HTTP testing, no independent
security oracle and no finding state modification. `scan` remains blocked.

## Host-side gates

- Snapshot is re-verified against the SQLite-pinned manifest and SHA-256 values.
- Exact relative path must be a `.py` file contained in the verified manifest.
- File is re-opened as a regular file; before/after file metadata and SHA-256 are
  checked. Source is strictly UTF-8, at most 96 KiB; job protocol max 256 KiB.
- `--execute` is mandatory. No repo-defined shell, build, npm scripts or hooks.
- Untrusted bytes are sent only to existing DockerBroker; no source execution
  on host, host bind mount, Docker socket access or network within container.
- The broker pins the local image ID and checks its security settings before
  running. Receipt binding to snapshot ID, file hash, manifest hash, entry and
  generated probe ID is re-audited from a saved host file after execution.
- Timeout, output truncation, transport errors, OOM, receipt mismatch and failed
  cleanup block the result. No success is emitted on missing evidence.
- Even exit code 0 has `EXECUTED_UNTRUSTED` and `security_verdict=NOT_EVALUATED`,
  not `PASS`, `SAFE` or `FIXED`. Stdout is never interpreted as proof.

## Key limitations

Only a *single* standalone file is supported. Local imports are not staged;
Python frameworks/dependencies are not installed. The source is renamed to
`task.py` in the ephemeral runtime. On Windows, copy/verify still cannot protect
against an adversary with control over the trusted host state or intentional
hostile concurrent edits (documented S6.2 limitation). Containers reduce risk,
but do not prove absence of sandbox escape. The Docker image was confirmed in
older S2/S5 workflows; a new live S6.3a run is **not yet verified on Windows**.
The local unit tests use simulated Docker transport, not live Docker.

## Manual Windows acceptance

Install overlay files from ZIP into existing project WITHOUT deleting
`.securitylab`, existing Docker model volume or state.

```powershell
py -3 -m unittest discover -s tests -p test_probe.py -v
$state = Join-Path $env:TEMP 'SecurityLab_S63a_DemoState'
$project = py -3 -m securitylab --state "$state" repo add '.\examples\s6_repos\python_standalone' --name 'Standalone fixture' | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'repo add failed' }
$snapshot = py -3 -m securitylab --state "$state" repo snapshot $project.id | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'repo snapshot failed' }
py -3 -m securitylab --state "$state" repo verify-snapshot $snapshot.snapshot_id
if ($LASTEXITCODE -ne 0) { throw 'snapshot verification failed' }
py -3 -m securitylab --state "$state" repo probe $snapshot.snapshot_id --entry main.py --execute
```

Expected when Docker image `securitylab-demo:local` is installed and broker
works: `status=EXECUTED_UNTRUSTED`, `exit_code=0`, `cleanup=PASS`,
`security_verdict=NOT_EVALUATED`. If image missing, do not silently pull another
image; examine `docker image inspect securitylab-demo:local` and build only
with deliberate operator action. If status is BLOCKED, inspect reported error
and the trusted receipt; do not relax isolation settings to force success.
