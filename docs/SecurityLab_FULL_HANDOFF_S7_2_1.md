## 1. Задача продукта и неизменные решения

SecurityLab — **локальная расширяемая система тестирования безопасности разных пользовательских программных проектов** на Windows с Docker. Общий маршрут: подключить копию репозитория → инвентаризовать технологии → сделать проверяемый snapshot → определить разрешённый профиль запуска → Red формирует гипотезу → независимый проверяющий воспроизводит нарушение на baseline → Blue предлагает фактический patch → изолированная проверка и повторная проверка → сохранение diff и Git-коммита **в отдельной ветке** → человек изучает результат через **Dashboard**. Поддержка новых стеков расширяется адаптерами, а не изменениями ядра под один проект.

- **SecurityLab** — внешний доверенный оркестратор: задания, политика безопасности, DockerBroker, результаты, Git, очередь и будущий UI.
- **Hermes** — агентная платформа для отдельных вызовов ИИ, **не** единоличный оркестратор всей последовательности. **Ollama/Qwen** — локальная модель, две последовательные роли Red/Blue, изолированные контексты.
- **Независимая проверка** программная и отделена от Blue. Blue не назначает себе `FIXED`, не меняет защищённые критерии/политику, не получает Docker socket, shell хоста, production-секреты или прямой доступ в production. **CS AIReviewer и третья AI-команда исключены.**
- Не сливать автоматически исправления в `main`; не удалять `.securitylab` и локально загруженную Qwen при обновлениях.
- **Dashboard обязателен** как главный интерфейс V1, CLI и отчёты сохраняются. Произвольный `scan` пока заблокирован и не может считаться готовым.
- Обещания «тестирует любой стек», «находит все уязвимости», «Docker неуязвим» не допускаются. Любой `PASS` относится к указанным проверкам и среде.

### 3.3 Содержание `candidate.py` — причина отказа доказана

Файл Blue в точности таким был прислан пользователем:

```python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()
RECORDS = {
    'one': {'owner': 'alice', 'value': 'synthetic-A'},
    'two': {'owner': 'bob', 'value': 'synthetic-B'},
}

@app.get('/records/{record_id}')
def read_record(record_id: str, x_test_user: str | None = Header(default=None)):
    if x_test_user is None:
        raise HTTPException(status_code=401)
    record = RECORDS.get(record_id)
    if record is None:
        raise HTTPException(status_code=404)
    # Deliberately missing record ownership check (safe test data only).
    return {'id': record_id, **record}
```

`git diff --no-index` относительно `examples/s7_repos/authz_vulnerable/app/main.py` показал **только**:

1. Удалён верхний docstring `"""Synthetic intentionally vulnerable API: never use with real user data."""`.
2. Удалена пустая строка перед декоратором.
3. Удалён завершающий перевод строки.
4. **НЕ добавлена проверка владельца**, несмотря на понятный Red-case. Строка `return {'id': record_id, **record}` осталась без предшествующей авторизационной проверки.

Предупреждения Git про LF/CRLF на Windows информационные; к отказу проверки отношения не имеют.

**Следствие:** причина текущего `NEEDS_REVIEW` — **неработающий патч Blue**, а не неправильный Docker image, не отказ Red и не ложное срабатывание независимой политики. Это подтверждено одновременно исходным текстом кандидата, diff и двумя реальными внешними HTTP-наблюдениями.

Пример правильной *проверки как концепта* — сопоставить текущего пользователя с `record["owner"]` до отдачи записи; однако **автоматически вставлять эталонный патч вместо результата Blue запрещено**. Нужно улучшить способность AI к исправлению и независимую обратную связь.

## 4. Корневая архитектурная проблема S7.2 и согласованный следующий шаг

В **поставленном пользователю релизе** S7.2 (`8d389d6`) `securitylab/access_ai.py` делает: `adapter.ask(blue_req)` → сохраняет `candidate.py` → `_observe(..., 'candidate', ...)` → **если `status != ACCESS_POLICY_MATCHED`, сразу `NEEDS_REVIEW` и выход**. Повторный Docker-прогон `recheck` выполняется только после положительного результата первой проверки. В `hermes_adapter.py` уже есть другая логика ограниченных повторов при отклонении формата/контракта Blue, но она **не означает** повторную попытку после неудачи реального Docker-поведения. Не путать эти два случая.

**Текущая намеченная работа: S7.2.1 — добавить ограниченный повтор Blue после независимого функционального провала.** Это была последняя задача, обсуждавшаяся до передачи. На Windows не установлена и не проверена. Новый чат должен оценить/реализовать её на основе S7.2, без потери ограничений:

1. После `candidate` с корректными квитанциями, но `ACCESS_POLICY_VIOLATION_REPRODUCED`/другим явно классифицированным **логическим несоответствием**, сохранить неудачный код, SHA-256 и все receipts.
2. Передать Blue **краткую структурированную обратную связь**: какой разрешённый case не прошёл, конкретные наблюдавшиеся HTTP-статусы, что прежний ответ фактически не менял уязвимое поведение. Не подсовывать готовое решение, не давать модели менять политику/тесты, не использовать её самооценку как доказательство.
3. Разрешить **максимум одну дополнительную функциональную попытку Blue** (отдельно от транспорта/проверки JSON; спроектировать общий верхний предел попыток, чтобы случайно не удвоить бюджет до бесконечности). Сохранить новый ответ, новый хеш и отдельную проверку в Docker. Ограничения модели и исполнения не повышать без основания.
4. При корректном повторном патче: провести обычный независимый кандидат-test, затем **ещё один recheck**, повторную проверку snapshot, policy, model/ Docker receipts, runtime image IDs, diff и Git. `FIXED` только после всех положительных контрольных условий.
5. При повторном логически неверном патче — `NEEDS_REVIEW`; при тайм-ауте/некорректных данных/подмене/ошибке очистки — `BLOCKED` или предусмотренный fail-closed статус. Не повторять бесконечно, не создавать verified commit.
6. Нужны позитивные и негативные unit/mock-тесты: исходный кандидат не починил → второй исправил; оба неверны; подмена receipt; разные image IDs; нарушение лимита попыток; неверная схема; timeout; сохранение первоначального и второго evidence; отсутствие фиктивного `FIXED`.
7. После тестов собрать **небольшой ZIP overlay и полный Git bundle** с новым коммитом и обновлённым MD, дать **точные команды Windows** для установки, проверки unit и реального end-to-end. **Не утверждать, что проблема исправлена, до успешной проверки на Windows**.

Опционально уже после анализа стабильности можно улучшать prompt Blue: явное «измени семантику авторизации, не форматирование», структурированная обратная связь, проверка отсутствия семантического изменения. Но не заставлять модель писать один заранее выданный фикс и не заменять независимый verifier эвристикой текста.

## Реализовано в S7.2

- Новая команда `repo access-ai <snapshot_id> --entry ... --policy ... --execute` для **выбранного FastAPI-сервиса и одного изменяемого Python-модуля**. Выбор проекта и пути идёт через инвентаризацию и проверяемый snapshot; названия учебного репозитория не встроены в логику команды.

# SecurityLab — S6.2.1 Windows hotfix (актуальная точка, 09.11.2026)

**Код:** Git commit `facdc76` (родитель `f579f09` S6.2). Полный исходный
код в `SecurityLab_S6_2_1.bundle` из ZIP `SecurityLab_S6_2_1_Windows_Hotfix.zip`.

**Windows S6.2.1 ещё не подтверждён.** Вся информация S6.2 ниже — историческая,

## Почему нужен hotfix

На Windows пользователя версия S6.2 выдала `FAILED (failures=2, errors=9)`;
не удалось создать `repo snapshot`. Причина — сравнение `st_dev/st_ino`,
которые в `os.DirEntry.stat()` Windows имеют нулевые значения, с реальными
идентификаторами из `os.fstat()`; получался ложный `Source changed between enumeration and open`.
В Python 3.13 это документированная особенность. Из-за неудачного создания
снимка не появился `snapshot_id`, поэтому последняя PowerShell-команда
завершилась вторичной ошибкой отсутствующего аргумента.

## Исправлено

`securitylab/snapshots.py`: свежий `Path.lstat()` после просмотра каталога
с проверкой типа, размера, времени, запретом ссылок/reparse; затем строгое
сравнение свежего `lstat` с `fstat` открытого файла и проверка SHA-256.
Аналогичное исправление сделано для `verify_snapshot`. В
`tests/test_snapshots.py` добавлены два теста: эмуляция Windows zero-identity
для полного цикла и отказ при изменении исходного файла после просмотра каталога.

Готовый Docker-проект для Windows 11, которому пользователь подключает изолированную копию собственного репозитория. Система должна читать его структуру, находить предполагаемые проблемы, воспроизводить их, предлагать и проверять исправления, сохранять историю и давать человеку проверяемые изменения.

Целевой проект может включать backend, frontend, авторизацию, БД, очереди, внутренние API, файловое хранилище, конфигурацию и зависимости. **Наличие каждого компонента нужно выяснять из репозитория; нельзя выдумывать стек.** Исходное ТЗ допускало один сервис для первого MVP; последнее уточнение пользователя закрепляет универсальность платформы. Области анализа: конфигурация и архитектура, авторизация/права и изоляция данных, входные параметры/API и ошибки, операции с данными/транзакции, межсервисные границы доверия, зависимости и известные проблемы версий.

Находка должна иметь ID, название, сервис, место в коде, описание, причину, условия и тест воспроизведения, ожидаемое/фактическое поведение, серьёзность, рекомендацию, статус и доказательства. Гипотезы не смешивать с подтверждёнными проблемами.

Blue должен подготовить минимальный патч и регрессионный тест, проверить функциональность, сохранить коммит в отдельной ветке, передать на перепроверку. Создание коммита само по себе не закрывает находку.

## 8. Учебный пример и точные ограничения S5

Встроенный service.py содержит записи one → alice/synthetic-A и two → bob/synthetic-B. Исходная read_record проверяет None-user и наличие записи, но не владельца.

Фактически проверенное исправление:

```python
owner = record["owner"]
if user != owner:
    return 403, None
```

Оно стоит после 401/404 и перед успешным возвратом.

S5 допускает только неизменное объявление RECORDS и одну read_record с исходной сигнатурой. Ограничены размер текста и число AST-узлов. Допускаются if/return, сравнения, ограниченные логические выражения, обращение по индексу, присваивания локальным record/owner, единственный разрешённый вызов RECORDS.get(record_id). Запрещены импорт, произвольные имена/атрибуты/вызовы, вывод, файлы, циклы, рекурсия, декораторы, глобальные изменения и изменение контейнеров данных.

Это **ограничение возможностей кода**, не проверка корректности решения. Неисправленный или логически неверный, но допустимый модуль может попасть в тесты и получить NEEDS_REVIEW. Сбой исполнения/политики/доказательств → BLOCKED. Ни один из них не назначает FIXED.

15 сценариев: пользователи None/alice/bob/attacker/пустая строка × one/two/missing. Пустая строка здесь обрабатывается по правилам учебной функции; это не универсальная модель аутентификации.

Тестовая обвязка и модуль исполняются в одном Python-процессе контейнера. Ограничение языка исключает доступ кандидата к операциям подмены теста/вывода. **Нельзя снять этот фильтр и продолжать доверять stdout произвольного Python.** Для реального приложения нужна другая граница доверия: внешние наблюдения, отдельно защищённые тесты/проверяющие и контроль инфраструктуры.

S5 не доказывает корректность для всех входов; автор кода может подстроить логику под известные 15 сценариев. Тесты не являются секретными. `FIXED` относится только к заданной находке и проверенным условиям.

Хост, установленный Docker/Python/Git, код SecurityLab и каталог state доверенные. Хеши помогают связывать доказательства и выявлять изменения, но не защищают от владельца хоста, переписавшего все доказательства и базу.

## 9. Чего пока нет — не приписывать системе

- Чтение и осмысленный анализ произвольного реального репозитория; `scan` намеренно BLOCKED.
- Автоматическое обнаружение стека/сервисов, установка зависимостей и запуск реального проекта.
- Написание Red воспроизводящих тестов и Blue регрессионных тестов в текущем AI-режиме.
- Подтверждение неизвестной находки до передачи Blue в общем случае. Сейчас Red/Blue идут последовательно, baseline запускается в известном упражнении позднее.
- Новая AI-сессия Red для повторного анализа после Blue: recheck сейчас означает повтор программных тестов.
- Общая проверка произвольного патча независимо от контролируемого им runtime.
- Git-ветка и коммит именно фактического S5-кандидата: старый Git workflow S3 не заменяет эту интеграцию.
- Дашборд, API управления им и единое отображение S3/AI/S5.
- Полноценные resume/stop/retry всей AI/S5-очереди после рестарта. В S3 механизмы есть, но их нельзя автоматически считать перенесёнными.
- Общий обработчик контейнеров-сирот после жёсткого убийства хостового процесса.
- Проверенные GPU-профили, подтверждённые нагрузочные характеристики и гарантированное время inference.
- Готовая установка всего продукта одной командой с healthchecks/восстановлением и документированным обновлением.
- Все сервисы, многомодельность, параллельные агенты, CI-интеграция.

Историческая проблема качества (до S5.1): Red в реальном выводе перепутал владельцев в описании (написал, будто alice/one — чужой доступ), хотя structured user=attacker и record_id=one корректны. Нельзя показывать такой текст как проверенное объяснение. В будущем нужна проверка согласованности объяснения с фактами либо вывод подтверждённого сценария из структурированных данных.

### S5/S5.1: интеграционная контрольная точка пройдена

### S6: общая работа с репозиториями и расширяемое исполнение

- Создать подключение локальной копии репозитория и ограниченную инвентаризацию без исполнения: структура, языки, manifests, сервисы, существующие тесты и предполагаемые команды сборки.
- Отделить обнаружение технологий от разрешения исполнения. README и package scripts — недоверенные данные, а не разрешения на shell/сеть/доступ к хосту.
- Ввести конфигурацию проекта и профили технологий: подготовка, зависимости, build/start/test, healthcheck, синтетические данные, сетевые связи и лимиты. Точные поля проектировать и проверять; этот интерфейс ещё не реализован.
- Общие очередь, доказательства, ограничения и UI не должны знать owner/RECORDS/service.py. Учебный fixture остаётся тестовым примером.
- Начать с ограниченного набора поддержанных профилей и испытывать их на нескольких разных репозиториях. Например Python API и Node.js API — возможные кандидаты, не уже реализованная или окончательно согласованная поддержка.
- Для неподдержанного стека выдавать понятный статус и недостающие настройки. Отсутствие поддержки не означает, что приложение безопасно.
- Создавать воспроизводимый снимок/отдельную ветку; фиксировать ревизию, конфигурацию и исходные тесты.
- Спроектировать проверяющего с наблюдениями вне недоверенного процесса приложения. Для API — отдельный клиент и изолированная сеть с синтетическими учётными записями/данными. Статический анализ, API-проверки, unit-тесты и UI-проверки имеют разные границы доверия.
- Отдельно разрешать загрузку зависимостей при подготовке; проверки без внешнего egress по умолчанию. Не давать агентам Docker socket и production secrets.
- Проверить негативные случаи: подделка отчёта, изменение тестов, зависание, нарушение протокола, оставшиеся процессы. Они не должны приводить к FIXED.

Выход: несколько различных испытательных проектов подключаются через общие механизмы и заявленные профили, без патчей ядра под конкретные имена файлов. Начальная поддержка может быть узкой, но расширение должно требовать нового профиля/адаптера, а не переписывания системы. До реализации новой границы доверия не открывать произвольный scan и не отключать S5-фильтр.

### S7: полноценный Red/Blue цикл на поддерживаемых проектах

- Red получает ограниченный контекст и разрешённые инструменты чтения/запросов, не произвольный shell на хосте.
- Гипотеза → воспроизводящий тест → подтверждение на baseline **до** исправления.
- Зафиксировать исходный тест и критерии ожидания вне контроля Blue.
- Blue предлагает минимальный patch и дополнительный регрессионный тест; добавленные Blue тесты не являются единственным основанием успеха.
- Проверить фактический patch, сборку, обязательные/регрессионные тесты, исходное воспроизведение.
- Отдельный повторный этап Red с новым контекстом; его итог также должен ссылаться на выполненные проверки, а не только на мнение модели.
- Создать проверяемый коммит в отдельной ветке, сохранить diff/историю, обеспечить rollback без потери пользовательских изменений.
- Ограничить число циклов; неясные права/требования и невозможность воспроизведения отправлять на рассмотрение.

Выход: подтверждённые находки в нескольких испытательных проектах проходят общий цикл, некорректные предложения отклоняются, main не меняется. Названия проектов и точные приёмочные сценарии фиксируются до приёмки; нельзя выдавать прохождение одного fixture за универсальность.

### S8: дашборд и единая модель задач

Дашборд можно проектировать параллельно определению API, но его статусы должны отражать реальные данные. Основные экраны: состояние среды/модели, проекты, очередь и активная роль, находки с доказательствами, diff/коммит, результаты проверок, журнал и понятные причины остановки.

Действия: подключить разрешённую копию, запустить, остановить, повторить, открыть доказательства, просмотреть изменения и откатить допустимую рабочую ветку. Общий backend для UI и CLI; не плодить отдельные фиктивные состояния. Не давать веб-форме произвольные команды shell. Локальный доступ, защита управляющих операций и корректная обработка содержимого AI/репозитория.

Выход: пользователь проводит основной сценарий через UI, а CLI сохраняет требуемые возможности. Dashboard больше не откладывается неопределённо ради бесконечного расширения ядра.

### S9: устойчивость и эксплуатация

Объединить AI/S5 с постоянной очередью; корректные stop/retry/resume и лимиты; recovery после падения; обработка оставшихся контейнеров; healthchecks; диагностика модели, памяти и Docker; сохранение/очистка артефактов; резервная копия и миграции; pin/update зависимостей; CPU/GPU-профили по фактической машине.

Проверить Windows end-to-end, первый запуск, повторный запуск, обновление без потери state/model, длительные отказы и заполнение диска. Отдельно считать время и объём inference; не гарантировать сроки по одной пробе.

### S10: приёмка и выпуск V1

Собрать полный пакет, инструкции, пример проекта и отчёта, матрицу требований/проверок/ограничений. Пройти критерии следующего раздела. Только после этого объявить первую рабочую версию завершённой.

## 12. Когда проект считается завершённым

Нужно различать три точки:

1. **Учебный прототип:** проверенная ограниченная цепочка на встроенном примере. Полный ограниченный S5.1-цикл уже прошёл на ПК пользователя, но это не весь продукт.
2. **Завершённая V1/MVP по согласованному объёму:** общая рабочая система для разных репозиториев в рамках явно заявленного набора поддерживаемых профилей, с интерфейсом, Git, проверками и эксплуатационными инструкциями. Предлагаю использовать именно эту точку для окончания основной разработки первой версии.
3. **Развитие V2/V3:** многосервисность, масштабирование и новые модели. Их не следует бесконечно добавлять в условия завершения V1.

Подключение нового проекта поддерживаемого профиля не требует изменения ядра.

Завершение не означает «найдены все уязвимости», «ИИ никогда не ошибается», «поддерживается любой стек» или «Docker невозможно взломать». Эти обещания не являются достижимыми критериями приёмки.

## 13. Развитие после V1

### V2 — несколько сервисов и более удобная эксплуатация

Подключение нескольких сервисов, временных БД/очередей и синтетических данных; проверка межсервисных прав; категории/приоритеты находок; расширенный Dashboard; сравнение запусков и экспорт отчётов; плановые проверки. Параллельность — только для независимых задач с реальным ресурсным бюджетом, а не одновременная загрузка нескольких больших моделей на ограниченный GPU.

### V3 — специализация и качество

Несколько локальных моделей/профилей задач, оценка качества на независимом наборе примеров, меньше ложных находок, статистика повторяющихся причин, более строгие критерии патчей и расширенные отчёты. Выбор модели по измерениям качества/скорости/памяти, а не только по размеру.

### Возможные дополнительные направления, пока не согласованы как обязательные

CI-интеграция и проверка изменений по коммитам; плагины для новых стеков; подключение проверенных анализаторов зависимостей/секретов; уведомления; работа с Git-hosting; облачная модель как явно разрешаемый режим. Не передавать код в облако автоматически. Не добавлять коммерческий SaaS, многопользовательскую платформу или автослияние без нового запроса.

Развитие планировать после измерения реальной полезности V1: сколько подтверждённых проблем, сколько ложных, доля принятых патчей, время и ресурсы на запуск, число ручных вмешательств.

## 14. Как ИИ будет разбирать приложение и писать тесты

Согласованное направление: сначала инвентаризация и существующие тесты, затем целевые новые проверки для найденных проблем и важных функций. Не требуется полностью покрыть приложение тестами до начала поиска.

ИИ может предложить тест, но не становится единственным авторитетом ожидаемого поведения. Пример: право Alice читать запись Bob зависит от требований продукта. Если требования неизвестны, система запрашивает уточнение или оставляет находку на рассмотрении. Автоматический валидатор умеет проверить исполнение и результат, но не всегда правильность придуманного моделью бизнес-правила.

Разделять исходные независимые контрольные тесты, тесты воспроизведения Red и дополнительные тесты Blue. Запрещать Blue «исправлять» контрольный тест, чтобы получить зелёный результат. Покрытие тестами — показатель, но не доказательство безопасности.
