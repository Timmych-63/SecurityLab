# SecurityLab S7.1 — независимый baseline для политики доступа

**Дата:** 2026-11-09. **База:** S6.3d `1ee7265`.

## Подтверждено на Windows до этого обновления

Пользователь запустил S6.3d: 17/17 тестов, оба Docker-образа пересобраны,
`fastapi-package-probe` с тремя HTTP-запросами вернул `HTTP_CHECKS_PASSED`,
`cleanup=PASS`, `security_verdict=NOT_EVALUATED`. Это относится к S6.3d,
а не к новой S7.1.

## Что добавлено

Команда `repo access-baseline` проверяет *заданную человеком* политику
чтения ресурсов через существующий проверенный снимок и S6.3d
Docker-профиль FastAPI-пакета. Политика — ограниченный JSON-файл
**вне** проверяемого исходного репозитория и state. Она не создаётся и
не правится Red/Blue. В схеме есть идентификатор проверки, синтетический
субъект, путь, HTTP-статус и ссылка denied-запроса на контрольный запрос
владельца того же ресурса. Контроль содержит заранее зафиксированный
ожидаемый SHA-256 тела ответа. Пример —
`examples/security_policies/record_ownership.json`.

В изолированной временной внутренней Docker-сети запускается сервис
FastAPI с набором `.py` файлов (ограничения S6.3d неизменны) и отдельно
минимальный контейнер фиксированного HTTP-проверяющего. Проверяющий
передаёт только синтетический заголовок `X-Test-User`, наблюдает HTTP-код,
размер тела и SHA-256 до 4096 байт; не открывает никаких портов на хосте.
Исходный код программы не получает доступ к проверяющему или Docker socket.

Если оба контроля подтвердили ожидаемые тела, а чужой субъект получил
`HTTP 200` **с идентичным полным телом контрольного ответа**, итог —
`ACCESS_POLICY_VIOLATION_REPRODUCED`, `POLICY_VIOLATION_OBSERVED`,
`finding_status=REPRODUCED`. Это воспроизведение *несоответствия
заранее заданному требованию*, не доказательство всех аспектов безопасности.
Если все наблюдения соответствуют политике — `ACCESS_POLICY_MATCHED`,
`NOT_PROVEN_SAFE` (не `FIXED`). Если контроль не прошёл или неожиданный
ответ не совпал с контрольным телом — `NEEDS_REVIEW`. Если Docker,
квитанции, очистка или доказательства невалидны — `BLOCKED`.

Политика ограничена максимум 8 GET-запросами, статусами 200 и 401/403,
синтетическими актёрами ASCII `[A-Za-z][A-Za-z0-9_-]{0,31}`; не
поддерживает настоящую авторизацию (сессии, cookies, OAuth, JWT), POST,
динамические БД и секреты. Не передавать production-пароли или токены.
Тело ответа целиком должно помещаться в 4096 байт и совпадать с
ожидаемым контрольным SHA; иначе не выдаётся подтверждение.

Схема и снимок привязываются по SHA-256 к Docker-квитанции. Исполняется
исходный код проверяемого проекта, а не canonical FIXED; не следует
полагаться на stdout приложения. Автоисправление и новая модель Red пока
не добавлены. Общая команда `scan` остаётся `BLOCKED`.

## Локальная проверка разработчика

- 17 новых тестов S7.1: позитивная/негативная классификация,
  неверный эталон, подмена тела/актора/receipt, отсутствие --execute,
  изменение снимка, неполная очистка, защита policy файла;
  отдельная проверка настоящего Python HTTP verifier через loopback
  без Docker.
- Следует запустить быстрый регрессионный пакет S6: `test_repository`,
  `test_snapshots`, `test_probe`, `test_http_probe`, `test_fastapi_probe`,
  `test_package_probe`, `test_container_runner`.
- Docker daemon в текущей среде разработки недоступен. Unit-тесты Docker
  используют фиктивный транспорт, не являются реальным Docker E2E.
  Старые AI-тесты с длинными тайм-аутами не следует засчитывать как PASS.

## Установка поверх S6.3d

Из ZIP-обновления скопировать содержимое `securitylab`, `tests`, `examples`,
`docs` в одноимённые папки. `.securitylab` и тома Ollama не трогать.
**Docker-образы пересобирать не требуется:** обновлённый фиксированный HTTP
verifier передаётся доверенным хостом через `docker create ... python -c` и
не встроен в образ. Образы, успешно собранные для S6.3d, остаются годны.
Hermes/Ollama/Qwen также не трогать.

```powershell
py -3 -m unittest discover -s tests -p test_access_baseline.py -v

$state = Join-Path $env:TEMP 'SecurityLab_S71_DemoState'
$policy = '.\examples\security_policies\record_ownership.json'
$p = py -3 -m securitylab --state "$state" repo add '.\examples\s7_repos\authz_vulnerable' --name 'S7 vulnerable synthetic' | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'repo add failed' }
$s = py -3 -m securitylab --state "$state" repo snapshot $p.id | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'snapshot failed' }
py -3 -m securitylab --state "$state" repo access-baseline $s.snapshot_id --entry app/main.py --policy "$policy" --execute
# Intentionally vulnerable baseline: exit code 3; this is an observed policy failure.

# Separate corrected synthetic example: must get ACCESS_POLICY_MATCHED (exit 0).
$p2 = py -3 -m securitylab --state "$state" repo add '.\examples\s7_repos\authz_fixed' --name 'S7 fixed synthetic' | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'repo add fixed failed' }
$s2 = py -3 -m securitylab --state "$state" repo snapshot $p2.id | ConvertFrom-Json
if ($LASTEXITCODE -ne 0) { throw 'snapshot fixed failed' }
py -3 -m securitylab --state "$state" repo access-baseline $s2.snapshot_id --entry app/main.py --policy "$policy" --execute
```

**Ожидания:** уязвимый проект — `ACCESS_POLICY_VIOLATION_REPRODUCED`
и `cleanup=PASS`, код завершения 3; исправленный — `ACCESS_POLICY_MATCHED`,
`cleanup=PASS`, код завершения 0. Оба запуска — независимые измерения
двух заранее подготовленных репозиториев, **не** проверка созданного Blue
патча. Объединённый Red/Blue цикл пока не реализован.
