# SecurityLab S9.1 — самостоятельный подбор сценариев доступа

## Что изменилось

Раньше Red выбирал готовый check_id из списка оператора. Теперь добавлен отдельный режим `access-ai-discovery-v1`:

1. Оператор задаёт описание приложения, пользователей и роли, ресурсы и их владельцев, роли с правом чтения. Контекст лежит вне проверяемого проекта и state.
2. Red получает выбранные Python-модули и правила, но не готовые проверки, не хеши ожидаемых ответов и не список известных дефектов.
3. Red предлагает до трёх гипотез: файл, описание, путь ресурса и пользователь.
4. SecurityLab проверяет пути, пользователей и правила. Ожидаемые статусы модель не задаёт. Для чужого ресурса ожидается 403; разрешённые читатели получают контрольные проверки на 200 и ожидаемое содержимое.
5. Независимый Docker-исполнитель проверяет исходный снимок. Только совпадение реально выданного запрещённому читателю тела с разрешённым контрольным ответом подтверждает нарушение этого типа.
6. При воспроизведении Blue предлагает изменения существующих модулей. Проверяется именно предложенный код, затем выполняется повторная проверка. Патч остаётся в изолированной Git-ветке, исходный проект не изменяется.

Старые режимы с готовыми политиками сохранены. В UI режим определяется выбранным документом правил; для контекста поиска автоматически включается несколько файлов.

## Границы этого шага

Это ограниченная самостоятельность, а не универсальный аудит: модель выбирает подозрительные комбинации из описанных ресурсов/пользователей. Самостоятельное обнаружение произвольных маршрутов, создание пользователей и данных, POST/PATCH, SQLi, XSS, загрузки файлов и неизвестные технологические стеки пока не реализованы.

Лимиты: 8 Python-модулей / 18 000 байт, 12 пользователей, 12 ресурсов, 3 гипотезы, максимум 8 HTTP-проверок вместе с контролями разрешённых читателей. Если контроли не помещаются, предложение отклоняется и модель может уменьшить число гипотез. Требуется одинаковое ожидаемое тело GET-ответа для всех разрешённых читателей выбранного ресурса. Персонализированные ответы требуют другого контракта.

`X-Test-User` явно объявлен заменой доверенного механизма идентификации на стенде. Перебор тестовых имён не считается взломом авторизации этого стенда. Проверка реальной аутентификации — отдельный будущий профиль.

Контекст содержит хеш ожидаемого ответа по публичным тестовым данным. Его задаёт оператор, а не модель и не исходный потенциально уязвимый сервер. Для TicketDesk использованы публичные исходные данные всех четырёх читаемых ресурсов. Нет списка уязвимых файлов, пометок «здесь ошибка», приватных ответов или эталонных патчей.

`FIXED` относится только к выполненным сценариям; это не подтверждение безопасности всего приложения. Остальные маршруты и регрессии не считаются проверенными. Пустой ответ Red даёт `NEEDS_REVIEW / NOT_EVALUATED`, а не «уязвимостей нет».

## Повтор и доказательства

Неверный формат/путь ответа Red в новом режиме допускает одну корректирующую попытку после подтверждённой очистки контейнера. Таймауты, отмена и ошибки транспорта автоматически не повторяются. Лимиты Blue прежние.

В `access_ai/<run_id>/` сохраняются `discovery_request.json`, `generated_policy.json`, summary, квитанции вызовов, исходный пакет, кандидаты, патчи, исходные/повторные наблюдения. Хеш внешнего контекста сохраняется отдельно от хеша сгенерированного плана. Изменение контекста или плана во время проверки блокирует результат.

## Установка поверх S9

1. Остановить dashboard (Ctrl+C в его окне). Активные проверки сначала остановить через UI.
2. Сохранить резервную копию текущей папки проекта.
3. Скопировать **содержимое** папки `update` из архива в корень SecurityLab с заменой файлов. Не заменять папку проекта целиком. Настройки модели, state и GPU override архив не содержит.
4. В PowerShell из корня SecurityLab:

```powershell
py -3 -m unittest discover -s tests -p "test_discovery.py" -v
docker compose -f compose.ai.yaml --profile build build hermes
docker compose -f compose.ai.yaml -f compose.ai.gpu.yaml up -d model
```

Если Docker не запущен: `docker desktop start`, дождаться готовности `docker version` с разделом Server. Если GPU override у тебя не используется — запускать model только с `-f compose.ai.yaml`.

5. Запустить dashboard с прежним state:

```powershell
py -3 -m securitylab.dashboard --state "$env:TEMP\SecurityLab_S72_DemoState"
```

6. Открыть http://127.0.0.1:8765 и обновить страницу Ctrl+F5.
7. «Новый запуск»: TicketDesk → его снимок → `app/main.py` → правила **«Поиск сценариев · ticketdesk-discovery»** → своя конфигурация модели. Профиль должен показывать самостоятельный выбор GET-проверок. Выполнить предпроверку, затем запуск.

TicketDesk и его снимок должны быть из предыдущего S9. Само тестируемое приложение обновлять не нужно. Приватный архив ответов не добавлять в проект, снимок или контекст модели.

Альтернатива через CLI (заменить значение ID снимка):

```powershell
$snapshot = 'ВСТАВЬ_ID_СНИМКА_TICKETDESK'
py -3 -m securitylab --state "$env:TEMP\SecurityLab_S72_DemoState" repo access-ai $snapshot --entry app/main.py --policy ".\examples\security_policies\ticketdesk_discovery.json" --discover --execute
```

## Что прислать после запуска

Итоговый статус и причину остановки, если она есть; желательно summary.json нового запуска. В нём `mode` должен быть `S9_ACCESS_DISCOVERY_PACKAGE`, `discovery.cases` — сценарии модели, `generated_policy` — проверки, составленные ядром. Нет необходимости присылать приватные эталонные исправления.

Успех инфраструктуры и успех модели различаются. `BLOCKED` из-за некорректной гипотезы/таймаута не доказывает отсутствие уязвимости; `NEEDS_REVIEW` после невоспроизведения также не означает безопасность приложения.

## Проверено при подготовке

128 Python-тестов затронутых наборов, сборка TypeScript/Vite, тесты UI запуска/смены модели и режима, бесшовного обновления, результатов и DTO. Исполнитель Docker и Hermes в тестах заменены контролируемыми имитациями; Git-проверки выполнялись реально. Живая модель, GPU, Docker и браузерная визуальная проверка в этой среде не выполнялись. Итог на твоём ПК ещё нужно подтвердить.

## Следующие шаги

1. Прогнать этот режим на TicketDesk и разобрать предложенные сценарии и реальные наблюдения.
2. Отдельно проверять полный набор регрессий приложения и приватную приёмку; не выдавать скрытые ответы агентам.
3. Добавить обнаружение маршрутов и предложения тестовых данных с проверяемым контрактом ожидаемого поведения.
4. Расширять исполнители по одному классу проверок: операции записи, роли/переходы состояний, затем другие типы уязвимостей.
5. Добавить поддержку дополнительных стеков и развёртывания приложений, сохраняя ограничения ресурсов, независимую проверку и запрет автоматического merge.
