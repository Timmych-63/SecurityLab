# Промпт для разработки дашборда SecurityLab — S8

Ты разрабатываешь веб-интерфейс существующего проекта SecurityLab. Сначала прочитай приложенные исходники и этот документ. Цель — рабочий интерфейс поверх существующей логики с честным отображением результатов. Не переписывай независимый проверяющий механизм и не подменяй его выводы AI-ответами.

## Проект простыми словами
SecurityLab — локальная лаборатория проверки безопасности собственных или разрешённых к тестированию приложений. Пользователь выбирает репозиторий, создаёт зафиксированный снимок, задаёт профиль запуска и политику доступа. Система воспроизводит нарушение, получает предложения Red/Blue через Hermes и модель, запускает исходный и предложенный код в ограниченных Docker-контейнерах и независимо проверяет результат. Успешный патч сохраняется отдельным коммитом в изолированной рабочей копии. Исходный репозиторий не изменяется автоматически.
Red анализирует проблему и предлагает сценарий, Blue предлагает исправление. Red не должен специально внедрять уязвимость в пользовательский проект. Модель не определяет итоговый FIXED. Hermes обслуживает AI-вызовы; SecurityLab отвечает за политику, этапы, выполнение, доказательства, Git и итоговый статус.
Долгосрочная цель — разные приложения через поддерживаемые профили; обещание «любое приложение уже поддерживается» недопустимо.

## Что реально есть сейчас
- Python CLI, JSON-результаты и часть HTML-отчётов; Docker-исполнение, ограничения и очистка контейнеров.
- Приём репозитория/снимки и профили проверки. Для AI-исправления доступа: один выбранный модуль небольшого FastAPI-приложения, внешняя политика оператора.
- Оригинальный кандидат Blue проходит независимую проверку без подмены эталонным исправлением; baseline, candidate, при необходимости candidate_retry, recheck.
- Ограничение двух попыток Blue, включая корректирующие попытки; успешный отдельный Git-коммит без merge/push.
- Журналы вызовов, привязки к снимку, политике, исходникам, тестам, образам и модели через хеши.
- AI-конфигурация из явно выбранного TOML: модель/digest, внутренний адрес сервера, сеть, контекст, лимит ответа, время вызова. Сейчас только Ollama-совместимый сервер внутри приватной Docker-сети, без API-ключей. Минимальный контекст текущего Hermes 64000.
- Успешный реальный AI-прогон с более узкой политикой был. Полный успешный AI-прогон расширенной политики на 8 проверок НЕ подтверждён: неверный первый патч и зацикливание второго ответа. BLOCKED не означает «проект безопасен».
- Готовые публичные REST API, WebSocket, очередь фоновых задач и удалённая многопользовательская система этим документом НЕ подтверждаются. Изучи код и отдельно предложи необходимые адаптеры.

## Задание и границы
Сделай настольный веб-интерфейс с адаптацией к телефону (чтение результатов и основные действия). Язык русский, технические идентификаторы сохраняются. Основной сценарий: проект → снимок/профиль/политика → запуск → наблюдение → разбор доказательств и патча.
Результат должен включать исходники, инструкции запуска, карту API и проверку интерфейса. Если доступен только frontend, реализуй отдельный типизированный адаптер и явный деморежим. Не изображай работающие серверные действия. Не добавляй подписки, оплату, команды сотрудников или облачную авторизацию.

## Экраны и функционал
### 1. Проекты
Список зарегистрированных проектов: имя, поддерживаемый профиль, последний запуск, время и результат. Добавление локального пути через локальный backend; браузерный выбор папки не выдавать за получение серверного абсолютного пути. Снимки, идентификаторы и время создания. Неподдерживаемый стек показывать с причиной. Не запускать чужой код при простом просмотре списка.
### 2. Новый запуск
Выбор проекта/снимка, сервиса, entry-модуля, профиля, политики и AI-конфигурации. Показывать границы проверки: «один модуль», число случаев, права субъектов. Предварительная проверка готовности Docker, нужных образов и модели с раздельными состояниями «обнаружен», «проверен», «ошибка», «не проверялся».
Перед выполнением показать параметры и действие «Запустить проверку». Не менять политику ради прохождения патча. Ошибки полей конкретные. Никакого произвольного shell-ввода в UI.
### 3. Запуски и ход выполнения
Фильтры по проекту, статусу, дате и режиму. В карточке запуска: run_id, snapshot_id, режим, начало/длительность, выбранная модель, текущая роль/попытка и установленный лимит времени. Этапы строить по реальным данным: порядок старта Red/baseline не выдумывать. Длительная генерация без событий — «ожидаем ответ», не искусственный процент готовности. История событий, обновление и потеря связи. Отмена доступна только после реализации backend-операции; ожидание отмены и подтверждённая остановка различаются.
### 4. Результат и доказательства
Раздельно показать статус выполнения, security_verdict и finding_status. PASS у smoke/проверки конфигурации не равен исправлению уязвимости. BLOCKED, NEEDS_REVIEW, TIMEOUT и NOT_EVALUATED не показывать зелёным.
Таблица проверок: сценарий, актор (включая анонимного), путь, ожидаемый/полученный HTTP-статус, совпадение тела/хеша, итог. Сравнение baseline/candidate/candidate_retry/recheck; отсутствующий этап обозначать «не выполнен», не «успешен». Контрольные случаи владельца, запрет чужого доступа и регрессии 401/404 показывать отдельно по смыслу.
Ссылки на доступные артефакты, JSON и существующие отчёты. Хеши/образ/digest/очистка в раскрываемом разделе «Технические доказательства». Не выдавать хеш за криптографическую подпись или гарантию отсутствия всех уязвимостей.
### 5. Предложения и изменения
Описание Red с отметкой «предложение AI», номер проверяемого сценария. Каждая попытка Blue: diff от исходного снимка, результаты её проверки, причины отклонения. Не показывать только последний кандидат, скрывая неудачи. Подтверждённый отдельный коммит/ветка при их наличии. Кнопка экспорта патча с проверенным содержимым. Нет автоматического merge/push и кнопки «принять как безопасное» в обход верификатора.
### 6. Настройки и диагностика
Модель/digest, адрес внутреннего Ollama-сервера, сеть, контекст, max_output_tokens, timeout_seconds; подписи с единицами и ограничениями. Показывать отдельно «файл конфигурации валиден» и «модель отвечает». Новый выбор действует на новые запуски, текущий сохраняет конфигурацию. GPU/CPU/память показывать только из реально полученных метрик; отсутствие данных — «нет данных». Никаких паролей/API-ключей в текущей форме.

## Визуальные требования
Спокойный профессиональный рабочий инструмент: читаемая типографика, плотные таблицы, ясная иерархия, компактная навигация. Не превращать в лендинг с огромным hero и декоративными метриками. Минимум вложенных карточек и лишнего пустого места. Цвет сопровождается текстом/иконкой. Светлая тема обязательна, тёмная желательна. Клавиатурная навигация, видимый фокус, контраст, корректный масштаб 125–150%, пустые/ошибочные/загрузочные состояния. Мобильная таблица должна сохранять доступ к данным, а не скрывать результат проверки.

## Интеграция и безопасность
Сначала изучи securitylab/cli.py, access_ai.py, ai_workflow.py, storage.py, hermes_adapter.py, ai_config.py и реальные summary/receipts. Создай таблицу «действие UI → существующая функция → нужный API-адаптер». Не парси человекочитаемый stdout как основной API. Проектируемые endpoint назови предложением, а не существующей реализацией.
Для первой локальной версии сервер слушает loopback, применяет проверки Origin/CSRF к изменяющим операциям. Не открывай Docker socket браузеру. Пути/артефакты разрешать через идентификаторы и контролируемые каталоги, запретить traversal. Репозиторий, ответы AI, логи, diff и HTML недоверенные: отображать текстом, не вставлять innerHTML; отчёты изолировать. Длинные задания должны идти через backend-исполнитель, не блокировать HTTP-запрос на 20 минут. Refresh не запускает задачу повторно. До реализации очереди разрешён один активный запуск с честным отказом второму. Не обещать восстановление задания после рестарта без серверной реализации.
Не загружать код проектов во внешние сервисы из браузера. Не отключать существующие лимиты, фиксацию digest, независимые проверки и очистку ради удобства интерфейса.

## Критерии приёмки
1. Пользователь понимает, какой проект, снимок, политика и модель использованы.
2. Успешный запуск и отказ показываются по реальным структурам данных; демоданные явно отмечены.
3. Можно просмотреть все попытки Blue, diff, независимые проверки и артефакты.
4. BLOCKED/TIMEOUT/неверный патч не становятся FIXED; smoke PASS не становится «уязвимостей нет».
5. Дубликаты запуска, перезагрузка страницы, недоступный backend, отсутствующая модель, длинная генерация и пропавший артефакт обработаны.
6. Сценарии XSS в логах/diff и traversal в путях не исполняются/не проходят.
7. Есть проверка основных действий на десктопе и телефоне, инструкция и список реально работающих/отложенных возможностей.

Сначала верни краткую архитектуру, карту интеграции и структуру экранов. Затем реализуй согласованный интерфейс. Если исходников нет, сделай демонстрационный frontend и контракт адаптера; попроси репозиторий для настоящей интеграции. Не выдумывай недостающий backend.
