# SecurityLab S10 — защитное ревью и функциональные регрессии

Обновление поверх S9.1.2. По последнему уточнению пользователя реализован защитный вариант трёх частей, а не автоматизация атак.

## Что входит

1. **Карта и подготовка приложения.** Статический разбор Python без импорта целевого кода на хосте: файлы, функции, параметры, имена вызовов, импорты, объявленные HTTP-маршруты. Проверка соответствия документированных ресурсов карте. Затем запуск исходной версии в существующем изолированном Docker-исполнителе и фиксированных функциональных проверок. Если исходная версия не проходит их, модель не вызывается.
2. **Пошаговое защитное ревью.** До пяти решений агента, включая финальные замечания. Только чтение фрагментов выбранных исходников и поиск буквального текста. Чтобы выдать замечание, агент сначала должен прочитать соответствующий файл. История ответов инструментов передаётся в следующий запрос. Нет инструментов HTTP-запросов, shell, установки пакетов, записи файлов или генерации тестовых действий.
3. **Патч и независимая приёмка.** Второй агент предлагает полное содержимое изменяемых существующих модулей. Ядро проверяет допуск, сохраняет точные байты, создаёт отдельную Git-копию, запускает фиксированные тесты и повторяет их в свежем окружении. При неудаче допускается ограниченная корректирующая попытка. Автоматического слияния с исходным проектом нет.

Изменения подключены к CLI и UI. В новом запуске выбрать **«Защитное ревью · ticketdesk-defensive»**. Профиль переключится на `defensive-review-v1` автоматически.

## Что проверяется

Тесты задаёт оператор вне проверяемого проекта и state. Для выбранных ресурсов проверяются обычные разрешённые чтения владельцем и разрешёнными ролями с точным ожидаемым телом ответа. Дополнительно — заданные оператором стандартные ответы 401/404. Новые файлы правил включают ожидаемые ответы из публичных тестовых данных.

В этом режиме агент не выбирает HTTP-запросы и не создаёт сценарии обхода защиты. Его замечания являются предложениями по коду, а не подтверждёнными уязвимостями. Допустимые проверки исполняет ядро, исходный код и патч работают только в Docker, не на хосте.

Успешный итог:
- `status: PASS` — процесс проверки патча завершился;
- `review_outcome: PATCH_PASSED_FUNCTIONAL_TESTS`;
- `security_verdict: NOT_EVALUATED`;
- `finding_status: null`.

Это не статус «приложение безопасно» и не доказательство исправления уязвимости. Пустое ревью, ошибка запуска, исчерпанный лимит и неуспешные тесты не считаются успехом. Сохранённые квитанции и хеши проверяются повторно; исходный проект не изменяется.

## Границы первой версии

- Python/FastAPI, до 8 модулей и 18 000 байт исходников.
- Статически объявленные маршруты непосредственно в точке входа; `include_router`, mount и динамическая регистрация пока отклоняются. Имена вызовов в карте не являются полным графом вызовов.
- Закреплённый образ FastAPI/Uvicorn; поддерживаются стандартная библиотека и зависимости этого образа. Неизвестные внешние импорты отклоняются до запуска. Автоматической установки произвольных requirements/скриптов репозитория нет.
- Начальные данные должны создаваться самим тестовым приложением при старте. Каждый пакет проверок получает свежий контейнер. Общая БД, очереди, миграции, внешние сервисы и загрузка пользовательских секретов не реализованы.
- До 32 фиксированных GET-проверок, пакетами по 8. POST/PATCH/браузерные сценарии и запуск полного pytest-набора проекта в этот профиль не входят.
- Ответы разрешённым читателям ресурса должны совпадать с заданным оператором хешем. Персонализированные ответы требуют другого контракта.
- До пяти решений ревьюера; чтение до 60 строк/4500 байт за действие, поиск до 15 совпадений с явным признаком усечения. Действуют лимиты размера общего контекста. До двух попыток Blue с учётом исправления формата. Срок каждого вызова задаёт существующая конфигурация модели; весь процесс может длиться дольше одного запроса.
- Старая модель может по-прежнему выдавать некорректные ответы. Работоспособность протокола не является гарантией качества её анализа.

Таким образом три части реализованы для защитного ограниченного профиля. Поддержка произвольных приложений, инфраструктуры и полных наборов тестов остаётся дальнейшей работой.

## Установка на Windows

1. Остановить активный прогон через UI, затем dashboard через Ctrl+C. Сохранить резервную копию папки проекта.
2. Скопировать **содержимое** `update` из архива в корень SecurityLab с заменой файлов. Не удалять папку проекта целиком. Настройки модели/GPU и состояние архив не заменяет.
3. Из корня SecurityLab выполнить:

```powershell
py -3 -m unittest discover -s tests -p "test_defensive_review.py" -v
docker build -f docker/Hermes.Dockerfile -t securitylab-hermes:s4 .
docker compose -f compose.ai.yaml -f compose.ai.gpu.yaml up -d model
```

Если Docker ещё не работает, сначала `docker desktop start` и дождаться раздела Server в `docker version`. Если GPU override не используется, запускать model только с `-f compose.ai.yaml`.

Образы `securitylab-demo:local` и `securitylab-fastapi:local` используются прежние. Если их нет:

```powershell
docker compose build
docker build -f docker/FastAPI.Dockerfile -t securitylab-fastapi:local .
```

4. Проверить наличие нового протокола в образе без запуска модели:

```powershell
docker run --rm --network none --entrypoint python securitylab-hermes:s4 -c "from securitylab.review_contract import TASK; print(TASK)"
```

Ожидается `s10-defensive-review-v1`.

5. Запустить dashboard:

```powershell
py -3 -m securitylab.dashboard --state "$env:TEMP\SecurityLab_S72_DemoState"
```

6. Открыть http://127.0.0.1:8765, обновить Ctrl+F5. «Новый запуск» → TicketDesk → существующий снимок → `app/main.py` → **«Защитное ревью · ticketdesk-defensive»** → своя модель → предпроверка → запуск.

Модель заново скачивать не требуется. Тестируемый TicketDesk и приватные эталонные ответы менять не нужно; приватные ответы в контекст не добавляются.

CLI-альтернатива:

```powershell
$snapshot = 'ВСТАВЬ_ID_СНИМКА_TICKETDESK'
py -3 -m securitylab --state "$env:TEMP\SecurityLab_S72_DemoState" repo review $snapshot --entry app/main.py --policy ".\examples\security_policies\ticketdesk_defensive.json" --execute
```

## Что проверить и прислать

В UI должны появиться этап карты, функциональная исходная проверка, шаги ревью, предложение патча, проверки кандидата и повтор. При пустом ревью/ошибке цепочка законно остановится раньше.

В разделе доказательств доступны `application_map.json`, `functional_plan.json`, `review_history.json`, запросы и квитанции модели, кандидаты, патчи и итоговый summary. Все пакеты функциональных проверок учитываются в таблице UI. Сам патч остаётся в изолированной Git-ветке.

Для разбора результата достаточно нового `summary.json` и текста причины остановки, если она есть. Старые запуски не переписываются.

## Верификация обновления

Прошли 150 Python-тестов затронутых наборов: 16 defensive review, 11 dashboard, 37 AI, 51 access, 16 discovery, 13 S8, 6 package. Дополнительно TypeScript/Vite build, тесты запуска и смены режима, бесшовного обновления/отмены, отображения результатов и DTO.

Модель и Docker в этих тестах заменены контролируемыми имитациями; Git и операции с файлами выполнялись реально. Проверены успешная цепочка, отсутствие вызова модели при неисправном baseline, остановка при регрессии/неуспешном повторе, подмена плана, отмена, лимиты действий, запрет произвольных инструментов и отсутствие ложного FIXED. Живой Docker/GPU/модель и визуальная проверка браузером здесь не выполнялись.
