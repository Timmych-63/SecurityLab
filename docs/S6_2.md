# SecurityLab S6.2 — bounded snapshots and inert profile plans

Date: 2026-11-09. Base commit `e2ffcd3` (S6.1). This is **not** a security
scanner for arbitrary projects; source execution is explicitly disabled.

## Implemented

- `repo snapshot <project_id>` makes a new, local copy under
  `<state>/snapshots/<snapshot_id>/workspace` and records its content SHA-256 per
  copied file in `<state>/snapshots/<snapshot_id>/manifest.json`.
- `repo verify-snapshot <snapshot_id>` compares the manifest hash against SQLite,
  checks all copied file SHA-256, counts, sizes, missing/extra files and
  directories, and rejects unexpected links/special files. It does not execute
  the sources.
- `repo snapshots <project_id>` shows snapshot metadata.
- `repo plan <snapshot_id>` verifies the snapshot first and inventories its
  copied files. Python and Node profile adapters are **planned only**; Go/Rust/
  Java remain detection-only. All build/start/test commands are `DISABLED`.
- SQLite gets an additive `project_snapshots` table without altering old runs,
  S5 findings or AI evidence. No model/Docker rebuild required.

## Protections and bounds

- 10,000 copied files, 20,000 directory entries, depth 12, max 8 MiB per file,
  128 MiB total, max 2 MiB manifest. Exceeding these means refusal and cleanup,
  **not** truncating the snapshot silently.
- Skip known sensitive filenames (`.env*`, `.npmrc`, private keys), existing
  dependency/generated/VCS directories, common secret directories, symlinks,
  junctions and nonregular files. Recheck metadata before and after copying.
- Source path and SecurityLab state must not be nested within one another for
  snapshotting. Original project files are never edited.
- Manifest and copied files stay local. No source is sent to Hermes, to Ollama,
  to the Internet, or to a shell. README and npm script contents are never
  executed or used as authorizing instructions.

## Security and correctness limitations

1. A local content-hashed copy is **not** a race-free, transactional filesystem
   snapshot. An actively hostile writer that alters files at the same time may
   bypass best-effort metadata checks. For now use a stable, trusted local copy.
2. SHA-256 plus a SQLite-recorded manifest hash detects accidental alterations,
   but a malicious actor with write access to both state and database can forge
   them. This is not a cryptographic attestation.
3. Filename-based secret exclusion is incomplete. Review code and data for
   secrets before sharing snapshots; do not point at production environments.
4. Skipped dependencies, secrets, large binaries and linked files can make a
   copy non-runnable. This is intentional in this preparatory stage.
5. The snapshot is **not** a Docker container, OS sandbox, Git branch or a
   working patch workspace. Generic Docker execution, independent service/API
   observations and Git branch management for real projects are future work.
6. `scan` remains blocked; existing S5.1 AI demo still applies only to its
   known fixture. This stage neither discovers vulnerabilities nor fixes them.

## Proposed S6.3

Build one verified, opt-in Python API runtime profile using a pinned image ID,
predefined, non-user-configurable DockerBroker operations, synthetic data and an
external verifier controlling requests and expected results. Separately prepare
Node adapter after negative tests of the Python runner. Keep host execution,
network access to production systems and Docker socket access by AI disallowed.
