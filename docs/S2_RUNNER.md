# S2 — одноразовый Python runner и доверенный broker

Это следующий этап разработки, не готовый AI-цикл. Hermes и модель ещё не подключены.

## Что реализовано

Broker запускается на стороне оператора, где доступен Docker CLI. Он выбирает уже
собранный образ `securitylab-demo:local`, фиксирует полный image ID, создаёт контейнер и проверяет inspect.
Контейнер не получает Docker socket, папки ПК, SQLite или том состояния.
Задание передаётся через stdin в JSON; файлы создаются в новом /work tmpfs.
Поддерживаются только плоские Python-файлы, обязательный task.py, до 32 файлов/256 KiB JSON.
Поля команд, mount, image и сетевых разрешений в задании запрещены.

В контейнере: UID 10001, network none, read-only rootfs, cap-drop ALL,
no-new-privileges, 512 MiB RAM и такой же total memory+swap limit, 1 CPU, 64 PID,
ограниченные tmpfs /tmp и /work. Логи Docker отключены, чтобы поток вывода не заполнял диск;
broker сохраняет ограниченный stdout/stderr. Отключение noexec на tmpfs не требуется:
Python читает исходник как данные. Это не означает запрет интерпретируемого кода.

После выполнения broker сверяет exit status с Docker daemon, удаляет контейнер и
проверяет отсутствие через daemon list. Ошибка удаления даёт CLEANUP_FAILED.
Тайм-аут/слишком большой вывод завершают attach, затем принудительно удаляется контейнер.
Намерение запуска сохраняется до create, итог — в .securitylab/isolated_runs/<ID>.json.

COMPLETED означает только завершение процесса с кодом 0. Вывод задания считается
недоверенным. Он не подключён к валидатору и не может закрыть находку как FIXED.

## Проверка на ПК

Из текущей папки проекта, после установки обновления:

```powershell
docker compose build
py -3 -m securitylab.container_runner --self-test
```

Вторую команду выполнять только после успешной сборки. Она создаст последовательно
пять одноразовых контейнеров: обычный запуск, exit 7, тайм-аут, превышение вывода,
проверка файловых/сетевых границ. Ожидается пять PASS и cleanup PASS для каждого.
У timeout-сценария также требуется маркер, что код реально успел запуститься.
Результаты остаются на ПК, сводка — .securitylab/isolated_runs/self-test.json.
Никакие модели или новые образы эта команда не скачивает.

Для собственного разрешённого синтетического задания предусмотрен `--job file.json`.
Это экспериментальный интерфейс; для этого этапа запускаем только встроенный self-test.
Универсальное сканирование проектов и выполнение AI-патчей пока закрыты.

## Ограничения и аварийное восстановление

Здесь нет защиты от всех уязвимостей ядра/Docker. Образы и хост доверенные.
Приложение внутри контейнера может подделать свой stdout и exit status; поэтому
успешный процесс сам по себе не служит доказательством исправления.
Исполнение Python не ограничено AST или запрещёнными import; граница — контейнер.

При Ctrl+C broker пытается удалить текущий контейнер. При принудительном убийстве
самого broker/отключении ПК finally может не выполниться. В записи намерения остаётся
имя контейнера. Посмотреть остатки: `docker ps -a --filter label=securitylab.ephemeral=true`.
Удалить выбранный остаток: `docker rm -f <точное имя securitylab-job-...>`.
Автоматический сбор таких остатков после перезапуска ещё не реализован.
Не использовать глобальный prune или удаление всех контейнеров.

Это Python-only runner без pip/dependency bootstrap, сетевых сервисов и базы данных.
Для других стеков нужны отдельные образы и контракты. Общая очередь и валидатор пока
используют прежний доверенный fixture runner; интеграция S2 с ними впереди.
Лимиты времени не являются точным real-time SLA: cleanup может добавить время Docker-команд.

## Проверки разработчика и источники

Unit/contract-тесты broker используют явно обозначенный FakeDocker и не считаются
контейнерными интеграционными испытаниями. Live self-test требуется на ПК пользователя.
Фактическое выполнение S1 уже подтверждено пользователем: 16 PASS,
прогон b4f21324bcaf419ea62cece28fecb87c.

Официальные интерфейсы:
- https://docs.docker.com/reference/cli/docker/container/create/
- https://docs.docker.com/reference/cli/docker/container/start/
- https://docs.docker.com/engine/logging/configure/
- https://docs.docker.com/engine/storage/tmpfs

Образ получает явное локальное имя в compose.yaml. Поиск образа не зависит от
наличия сохранённых контейнеров: прежние запуски с --rm не мешают S2.
