# Техническое задание: локальная AI-система автоматического тестирования безопасности проекта

**Версия:** 1.0  
**Платформа запуска:** Windows 11  
**Исполнитель:** разработчик инфраструктуры / AI-интеграции

## 1. Цель проекта

Разработать готовый к запуску Docker-проект, который разворачивает локальную систему AI-агентов для проверки безопасности собственного программного продукта.

Система должна выполнять цикл:

**Анализ проекта → поиск потенциальных уязвимостей → воспроизведение проблемы в тестовой среде → исправление → автоматические тесты → повторная проверка.**

В системе должны быть две основные роли:

- **Red Team** — исследует проект и обнаруживает проблемы безопасности.
- **Blue Team** — анализирует подтверждённые проблемы, исправляет их и проверяет результат.

Управление работой агентов осуществляется через оркестратор. Hermes Agent рассматривается как агентный CLI-компонент, который необходимо установить и интегрировать. На момент постановки задачи Hermes ещё не установлен.

## 2. Аппаратная конфигурация

Целевой компьютер:

- ОС: Windows 11.
- GPU: NVIDIA RTX 5060, 8 ГБ VRAM.
- RAM: 32 ГБ.
- CPU: Intel Core i5-14400 (требует подтверждения).
- Среда контейнеризации: Docker Desktop с поддержкой Linux-контейнеров.

Система должна учитывать ограниченную видеопамять. Для первой версии использовать одну локальную языковую модель в двух последовательных ролях Red Team и Blue Team.

Предусмотреть возможность в дальнейшем подключить дополнительные модели.

## 3. Что необходимо собрать

Разработчик должен предоставить единый проект со следующими компонентами:

1. **AI Runtime** — локальный запуск языковой модели.
2. **Hermes Agent** — управление агентными задачами и инструментами.
3. **Orchestrator** — управление очередью задач, состояниями и взаимодействием агентов.
4. **Red Team Agent** — анализ безопасности и подготовка отчётов.
5. **Blue Team Agent** — подготовка исправлений и регрессионных тестов.
6. **Git Integration** — чтение репозитория, создание веток и коммитов.
7. **Test Runner** — запуск тестов и проверок.
8. **Dashboard / Logs** — отображение текущих задач, найденных проблем и результатов.

## 4. Объект тестирования

Объектом тестирования является копия нашего собственного программного проекта.

Проект состоит из нескольких сервисов и может включать:

- Backend API.
- Frontend.
- Систему авторизации и управления пользователями.
- Базы данных.
- Очереди сообщений.
- Внутренние API между сервисами.
- Файловое хранилище.
- Конфигурацию и инфраструктуру.
- Сторонние библиотеки и зависимости.

Фактический список сервисов и используемых технологий разработчик должен получить из репозитория проекта. Нельзя предполагать, что все перечисленные компоненты присутствуют.

## 5. Области проверки Red Team

Red Team должен проводить контролируемый анализ собственного проекта в изолированном тестовом окружении.

### 5.1. Архитектура и конфигурация

- Анализ структуры проекта и взаимодействия сервисов.
- Поиск ошибочных настроек безопасности.
- Проверка разделения публичных и внутренних интерфейсов.
- Проверка конфигурации контейнеров и сетевых ограничений.
- Проверка наличия чувствительных данных в тестовой конфигурации.

### 5.2. Авторизация и доступ

- Проверка разграничения ролей пользователей.
- Проверка доступа к функциям, доступным только авторизованным пользователям.
- Проверка корректности серверной проверки разрешений.
- Проверка изоляции пользовательских данных.
- Проверка сценариев с недостаточными правами.

### 5.3. Входные данные и API

- Проверка серверной валидации входных параметров.
- Проверка обработки некорректных данных.
- Проверка обработки ошибок.
- Проверка ограничений размеров запросов.
- Проверка корректности ответов API.
- Проверка защиты от повторной обработки некорректных запросов.

### 5.4. Работа с данными

- Проверка корректности операций чтения и записи.
- Проверка изоляции данных разных пользователей.
- Проверка обработки ошибок базы данных.
- Проверка отсутствия избыточного раскрытия данных.
- Проверка корректности транзакций и обработки повторных операций.

### 5.5. Межсервисное взаимодействие

- Проверка границ доверия между сервисами.
- Проверка внутренней авторизации.
- Проверка обработки ошибок при недоступности соседнего сервиса.
- Проверка валидации сообщений и событий.
- Проверка корректности передачи пользовательского контекста.

### 5.6. Зависимости и качество кода

- Анализ используемых библиотек.
- Выявление известных проблем в версиях зависимостей.
- Проверка небезопасных участков кода.
- Поиск отсутствующих проверок и тестов.
- Формирование рекомендаций по снижению технических рисков.

## 6. Формат результата Red Team

Каждая найденная проблема должна оформляться отдельной записью:

- Уникальный ID.
- Название проблемы.
- Затронутый сервис.
- Файл и участок кода.
- Описание проблемы.
- Условия воспроизведения.
- Безопасный тест, подтверждающий проблему.
- Ожидаемое поведение.
- Фактическое поведение.
- Оценка серьёзности.
- Рекомендация по исправлению.
- Статус проверки.

Необходимо отделять подтверждённые проблемы от предположений агента.

## 7. Обязанности Blue Team

После получения подтверждённой находки Blue Team должен:

1. Изучить отчёт Red Team.
2. Проверить исходный код и связанные сервисы.
3. Подготовить минимальное исправление.
4. Добавить регрессионный тест.
5. Проверить, что существующая функциональность не нарушена.
6. Запустить доступные тесты проекта.
7. Создать коммит в выделенной Git-ветке.
8. Передать результат Red Team для повторной проверки.

Blue Team не должен самостоятельно закрывать находку только на основании факта изменения или коммита.

## 8. Цикл автоматической проверки

Для каждой находки должен работать следующий процесс:

1. Red Team создаёт находку.
2. Оркестратор регистрирует её и сохраняет тест воспроизведения.
3. Blue Team получает задачу.
4. Blue Team подготавливает исправление.
5. Изменения проходят автоматические тесты.
6. Blue Team создаёт коммит.
7. Red Team повторяет исходную проверку.
8. Оркестратор фиксирует результат.

**Условия закрытия:**

- Исходная проблема больше не воспроизводится.
- Регрессионный тест проходит.
- Сборка и обязательные тесты проекта проходят.
- Повторная проверка Red Team завершилась успешно.

Если проблема воспроизводится, задача возвращается в работу.

## 9. Git-интеграция

Необходимо реализовать:

- Подключение к локальной копии репозитория.
- Создание отдельной рабочей ветки для AI-изменений.
- Фиксацию каждой находки в журнале.
- Коммиты Blue Team с понятными сообщениями.
- Сохранение истории изменений.
- Возможность отменить изменения.
- Запрет автоматического слияния в основную ветку.

Все изменения должны оставаться проверяемыми человеком.

## 10. Docker-окружение

Разработчик должен подготовить:

- Dockerfile для необходимых компонентов.
- docker-compose.yml.
- Файл конфигурации `.env.example`.
- Отдельные тома для моделей, логов и рабочих данных.
- Проверку доступности GPU.
- Ограничения ресурсов контейнеров.
- Health checks для сервисов.
- Сценарий запуска и остановки.
- Сценарий очистки и восстановления тестового окружения.

### Требования к безопасности

- Не подключать контейнеры к рабочей инфраструктуре.
- Не использовать реальные пользовательские данные и производственные секреты.
- По умолчанию запретить исходящий сетевой доступ из тестового окружения, кроме явно разрешённых источников.
- Не монтировать системные каталоги Windows.
- Предоставлять агентам только необходимые права.
- Запретить автоматическое выполнение непроверенных изменений вне тестового стенда.
- Не предоставлять агентам доступ к производственным учётным записям.

## 13. Критерии приёмки

Проект считается готовым к первой демонстрации, если:

- [ ] Все необходимые контейнеры запускаются одной командой.
- [ ] Локальная модель отвечает на тестовый запрос.
- [ ] Hermes Agent запускается и взаимодействует с оркестратором.
- [ ] Red Team может анализировать выбранный тестовый сервис.
- [ ] Red Team умеет оформить подтверждённую находку.
- [ ] Blue Team может подготовить исправление в отдельной ветке.
- [ ] Автоматические тесты запускаются в контейнере.
- [ ] Red Team повторно проверяет исправление.
- [ ] Находка не закрывается только из-за создания коммита.
- [ ] Все действия сохраняются в логах.
- [ ] Рабочий проект и основная Git-ветка остаются нетронутыми.

## 15. Главный принцип проекта

Система должна не просто генерировать советы по безопасности, а демонстрировать проверяемый результат.

Каждая проблема должна иметь воспроизводимый тест, каждое исправление — регрессионную проверку, каждый коммит — историю изменений, а каждое закрытие задачи — подтверждение повторной проверкой.

**Ожидаемый результат:** один Docker-проект, который разработчик передаёт нам, мы запускаем на своём ПК, подключаем изолированную копию репозитория и получаем локальную AI-систему непрерывного анализа и улучшения безопасности собственного программного продукта.
