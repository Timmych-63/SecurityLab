# S6.2.2 — Windows SQLite test teardown hotfix (2026-11-09)

## Наблюдение на Windows пользователя

В установленной S6.2.1 команда `py -3 -m unittest discover -s tests -p test_snapshots.py -v`
выполнила 16 тестов успешно, но `test_restart_and_sqlite_snapshot_persistence`
завершился `PermissionError [WinError 32]` на удалении временного `state.sqlite3`.

## Причина

В `SnapshotTests.setUp()` использовалось `self.addCleanup(self.store.close)`.
Это регистрирует *привязанный метод* **первого** объекта Store. Тест
`test_restart_and_sqlite_snapshot_persistence` закрывал этот объект, затем
переоткрывал `Store(self.state)` и заменял `self.store`. После теста cleanup
повторно закрывал первый Store, но **не** новый. На Windows открытое соединение
SQLite мешает `TemporaryDirectory.cleanup()` удалить файл БД.

## Исправление

- `tests/test_snapshots.py`: регистрация cleanup через `lambda: self.store.close()`;
  объект определяется при выполнении cleanup, а не при регистрации.
- Добавлен `test_reopened_connection_closed_on_cleanup`: напрямую запускает
  зарегистрированные cleanup и проверяет, что новая связь SQLite закрыта.
  Этот тест специально воспроизводит проблему и **падает на Linux** со старой
  привязкой `self.store.close` (проверено), чтобы ошибка больше не зависела
  от поведения файловых блокировок Windows.
- Исполняемые модули приложения, SQLite schema, Docker, модель, CLI и политика
  безопасности **не менялись**. Никакая пользовательская БД не удаляется.

## Проверки

- Linux: 18/18 тестов `test_snapshots.py` PASS; 22/22 `test_repository.py` PASS.
- Отрицательная проверка: новый тест со старой строкой `self.addCleanup(self.store.close)`
  дал ожидаемый FAIL; после восстановления исправления PASS.
- Настоящая Windows-проверка S6.2.2 остаётся за пользователем.
- Старые длительные AI-integration тесты и full regression на S6.2.2 не запускались.

## Установка

Поверх S6.2.1 заменить **только** `tests/test_snapshots.py` из ZIP. Не заменять
`securitylab/snapshots.py` — установленный S6.2.1-фикс уже дал PASS.

В PowerShell в корне SecurityLab:

```powershell
py -3 -m unittest discover -s tests -p test_snapshots.py -v
```

Ожидается `Ran 18 tests` / `OK`. Затем можно повторить `repo add` →
`repo snapshot` → `repo verify-snapshot` на синтетическом `python_api` в
отдельном `%TEMP%` state с `VERIFIED_CONTENT_HASHES`.

ограниченного executor для объявленных профилей. `scan` по-прежнему BLOCKED.
